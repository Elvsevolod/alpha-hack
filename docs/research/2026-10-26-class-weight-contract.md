# Веса классов: от запроса агента к исполняемой модели

Общая ML-цель остаётся активной. Предыдущий goal-turn дал прогресс (`b4eeea4`: согласование идентичности frozen recipe). Этот этап проверяет реальные сохранённые ML-трассы и универсальный контракт передачи `class_weight`; не добавляет модельное семейство и не подбирает веса по внешней оценке.

## Основание и реальные свидетельства

По ТЗ один код должен самостоятельно решать неизвестные классификационные задачи, соблюдать подтверждённый формат меток и общий бюджет. Матрица первичных требований сохранена в `2026-10-26-agent-path-audit.md`. Перед изменениями также прочитаны актуальные отчёты другой ветки о workflow bottlenecks/fixes: уже исправленные там память веток, verifier feedback и подсказки параметров не выдаются здесь за новые находки.

Исторический SQLite `research_memory_ab_live_20261025/runs/bank_A` прочитан с `mode=ro`; исходные файлы/процессы не менялись. Подтверждённая metadata содержит классы `no/yes`. В двух реальных экспериментах агент передал LightGBM `class_weight={"1":2}` и затем `{"1":8}`; оба завершились KeyError. Это не низкое качество модели, а несовместимая с подтверждёнными метками команда, дошедшая до fit. Точный source SHA и ID записаны в `research/agent_path_audit_20261026/class_weight_contract.json` без исходных строк данных.

Независимый offline probe экспортировал **неизменённый предыдущий коммит `b4eeea4`** через git archive и обучал только синтетические данные. Он подтвердил два случая: ошибочная карта для строковых классов допускалась preflight и падала с KeyError; корректная карта для числовых классов после JSON (`{"0":1,"1":3}`) тоже допускалась, но падала, поскольку библиотеке нужны исходные числовые метки, а не строковые ключи JSON.

Документация через Context7 подтверждает смысл `{class_label: weight}`: [LightGBM](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.LGBMClassifier.html), [scikit-learn](https://github.com/scikit-learn/scikit-learn/blob/main/doc/glossary.rst). Это текущая документация, а не утверждение о версии страницы. Поведение проверено на фактически установленных **LightGBM 4.6.0 / scikit-learn 1.5.2**, включая чтение их соответствующих class-map/weight реализаций.

## Что изменено

- Неизвестные и неоднозначные ключи отвергаются до preprocessing/создания кандидата. Код не угадывает, что индекс `1` означает `yes`.
- Для подтверждённых числовых меток JSON-ключи восстанавливаются в исходные метки только однозначно. Decimal не сливает соседние большие целые через float rounding. Строковые метки остаются строковыми. Дублирующие алиасы и смешанная неоднозначность отклоняются.
- Значения должны быть конечными неотрицательными числами; bool и выходящие за представимый float диапазон не принимаются. Текущий fit должен сохранить положительный вес хотя бы одного наблюдаемого класса. У неизвестных ключей/невалидных значений не печатаются присланные значения.
- Перед созданием модели карта привязывается к меткам текущего target. Поддерживаемые forest multioutput-карты привязываются к outputs в подтверждённом порядке, а не целиком передаются каждому отдельному классификатору.
- Вес объявленного класса, отсутствующего в данном inner fit, не передаётся локальному class map. При этом исходный frozen рецепт сохраняет его: полный refit снова применяет вес, если класс появился. Это не удаление настройки и не использование контрольных меток.

Область исправления — `class_weight` у зарегистрированных LightGBM, LogisticRegression, SGD, RandomForest и ExtraTrees. Оно не объявляется полной проверкой CatBoost `class_weights`, XGBoost `scale_pos_weight` или всех возможных настроек весов.

## Проверки

Итоговый новый набор: **33 passed**. Проверены все пять семейств, числовые метки включая непоследовательные и обратный объявленный порядок, JSON round-trip, независимое соответствие столбцов native probabilities, большие ключи без потери точности, строковые метки, отрицательные/нечисловые/нулевые веса, редкий отсутствующий inner-класс и полный refit, multioutput forest и Optuna trial → frozen replay.

Реальный путь Controller → JSON request → worker → сохранённая модель проверяет типы переданных весов. Ошибочная карта не создаёт эксперимент, исправленная выполняет fit; реальных LLM calls — 0. Это ручной технический сценарий, а не доказательство, что Qwen сам исправит следующую команду.

До расширения кейсов связанный набор pipelines/contracts/research evaluation дал **77 passed**; ещё **3 passed / 32 deselected** проверяют blend/domain/window composition (название XML с `hpo_composition` не означает наличие HPO в этих трёх кейсах). Эти наборы пересекаются с новым и не суммируются.

Первый controller-тест ожидал неверное имя публичного статуса: продукт корректно возвращал `rejected`, а не `incompatible`. Позднее дополнительный Optuna-тест имел integer row index вместо строкового staged-контракта; fixture исправлена, production row-key guard не ослаблялся. Отрицательные XML сохранены, успешный расширенный набор — `class_weight_contract_final_v3.xml`.

Веса не оптимизировались, внешние метки не читались, повторного прогона исторического Qwen не было. Прирост Macro F1/RMSE не заявляется. Main, конкурсный ZIP, чужие процессы и старые frozen-серии остаются без изменений. Следующий незакрытый участок — причины провалов HPO/неисполненных намерений и их доставка следующему решению агента; общий goal не завершён.
