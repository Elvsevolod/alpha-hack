## Что подтвердилось и что осталось открытым

Реальный Qwen успешно прочитал `research_options` по предоставленному `ids`-маршруту. Старый сбой пустой source.version на этом шаге не повторился. Это живое подтверждение конкретного исправленного перехода, а не всех source-контрактов или автономной полезности.

Принятые команды: read leader pipeline → read research_options → повторное read leader pipeline → preview изменения `hyperparameters.class_weight = balanced` → ещё одно read leader pipeline. Между ними был один обрезанный ответ. Затем лимит шести обращений завершил поиск. Утверждать общую неспособность Qwen к исследованию при большем бюджете нельзя; в этом ограниченном опыте автономного эксперимента и выигрыша качества нет. Лимит не увеличивался в ходе run.

Проверка фактических wire JSON обнаружила разрыв передачи состояния. После первого чтения base recipe hash присутствует в request 2, но уже отсутствует в request 3 после другого чтения. Это соответствует явной доставке результатов и сжатию без полной conversational history. После preview request 6 содержит hash **нового** рецепта, но не исходный base_hash. Preview возвращает `base_id`, `pipeline`, `recipe_hash`, `diff`, `learned_state`, `status`; полного `apply_recipe` нет. Публичная инструкция требует скопировать ту же application, но сама прежняя команда в следующем запросе не сохранена. При этом `diff` не является RecipeApplication, а новый recipe_hash нельзя подставлять вместо исходного base_hash.

Это подтверждённый недостаток перехода preview→apply для stateless контекста. Он согласуется с повторным чтением базы, но причинность всех повторных чтений, единственная причина нулевого числа экспериментов и эффект исправления на реальный выбор не доказаны. Модель могла самостоятельно использовать полный нормализованный pipeline; нельзя утверждать, что обучение было вообще невозможно.

## Исправление после запуска

Успешный `resolve` теперь возвращает **точный `apply_recipe`** (`source`, `base_id`, исходный `base_hash`, typed changes) вместе с нормализованным pipeline/hash/diff. Публичное описание инструмента отличает изменённый recipe_hash от apply_recipe.base_hash и указывает копировать возвращённую application. Границы обучения не меняются: при train она снова проходит исходные проверки hash, доступности базы и совместимости. Не добавлены автоматический запуск, выбор гипотезы за Qwen или подстановка рецепта.

HTTP replay использует только payload текущего запроса: read base → preview → copy delivered apply_recipe → настоящий LightGBM fit с `class_weight=balanced` → finish/control/full refit/CSV. У fixture нет сохранённой application между шагами; проверяются разные base/result hashes, точное совпадение исполненного recipe hash и фактический параметр сериализованной модели. Native и JSON проверены с обычным контекстом и compaction level 2. До исправления **4 failed**, 20,62 s; связанный набор после — **11 passed**, 67,95 s, включая прежние recipe guards и source-recovery loop. Новые ответы задаёт mock: это техническая проверка, не свидетельство самостоятельного восстановления реального Qwen. Последующий live run с этим новым исправлением ещё не выполнен.
