# AutoGluon GBM: alias числа раундов перекрывал выбранное расписание

На исходниках `1e6f564` реальный AutoGluon 1.3.1 / LightGBM 4.6.0 воспроизвёл цепочку: inner fit выбрал **1 раунд**, немедленный refit на всех 100 разрешённых строках обучил **30**, fresh refit на 120 строках снова обучил **30**. Лимит явной конфигурации был n_estimators=30. Значение не потерялось: оно осталось лишним alias и перекрыло выбранное значение num_boost_round=1 в native LightGBM.

Таким образом, inner selection и фактическое выполнение расходились. До исправления итоговый metadata-рецепт мог содержать одновременно n_estimators=30 и num_boost_round=1. Этот probe не доказывает различие между внешней validation-моделью и опубликованной моделью: обе стадии refit здесь получили 30 раундов. Подтверждён именно срыв выбранного внутреннего расписания и неоднозначность сохранённого рецепта, с риском неверного прогноза стоимости.

## Причина и изменение

Наша проверка явного portfolio нормализовала параметры к sklearn-именам прямого LightGBM. Но native AutoGluon LGBModel использует num_boost_round, объединяя исходные параметры с hyperparameters_fit при refit. LightGBM при наличии n_estimators/num_iterations выбирает alias из params вместо переданного числа раундов.

На границе AutoGluon GBM теперь происходит единственная нормализация: n_estimators / num_iterations / num_boost_round → **num_boost_round**. Конфликтующие значения отклоняются; одинаковые объединяются. Исходный PipelineSpec не мутирует. Это не новый HPO и не изменение выбранного числа: поиск задаёт cap, после остановки AutoGluon заменяет его фактически выбранным числом. Прямые LightGBM/Optuna адаптеры не менялись. Публичная схема описывает alias-контракт; registry version 5 инвалидирует прежнюю оценку совместимости.

## Проверки

До изменения — один реальный failing regression test с последовательностью 1 / 30 / 30. После изменения:

- **8 passed**: три имени параметра × regression/Macro F1; в шести сценариях реальные fits на 60/100/120 строках сохраняют 1 / 1 / 1, measured tree count совпадает с params_trained; ещё две проверки конфликтов и неизменности исходного запроса.
- Финальный связанный набор **19 passed, 21 deselected**, включая прежние AutoGluon selection/refit, native weights boundary, default/explicit portfolio, реальные bagging/stacking exact-group graph replay и сериализацию. Наборы пересекаются.

Сценарии синтетические, с преднамеренно противоположной зависимостью во внутренней validation, чтобы остановка выбрала меньше cap. Это tripwire корректности, не независимый benchmark качества и не перенос на организаторские данные. Все внутренние решения находятся в разрешённой обучающей популяции. Память и полная стоимость запуска в этом этапе не измерялись; 30→1 раунд нельзя выдавать за 30-кратное ускорение агента.

Среда та же изолированная native Python 3.12 с AutoGluon packages 1.3.1 и setuptools 75.8.2 из предыдущего аудита, не полный Linux-контейнер конкурса. Основная venv, requirements, чужие процессы, данные, ZIP и production PyTorch не менялись. Уже обученные старые артефакты автоматически не переписываются; для нового исследования нужен fresh fit исправленного portfolio. Миграция ранее обученных alias-артефактов этим этапом не сертифицирована.

Реальных Qwen API calls: **0**, alpha-api-limits для офлайн-проверок не требуется. Organizer quality gain и самостоятельный выбор Qwen не заявлены. Общая цель остаётся активной.
