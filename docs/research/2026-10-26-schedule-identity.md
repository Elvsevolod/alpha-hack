# Согласование выбранных итераций и реально оцениваемой модели

Общая цель улучшения ML-агента остаётся активной. После исправления HPO feedback проверен переход «внутренний выбор → оцениваемая модель → frozen recipe → повторное обучение». Это соответствует требованиям самостоятельного исследования и честной внутренней валидации из ТЗ, сопоставленным с первичными материалами в `2026-10-26-agent-path-audit.md`. Расширение production DL не выполняется.

## Доказанные расхождения

Источник находок — текущий код и синтетические воспроизведения, а не новая серия на control организаторов. Этим дефектам не приписывается исторический organizer score без доказательства.

1. Внутри native early stopping для **HistGradientBoosting** warm-start модель продолжала расти после лучшего checkpoint. В воспроизведении рецепт замораживал **2** итерации, но объект, которым оценивался inner trial, содержал **4**. В обычном direct-пути последующий полный fit мог маскировать ошибку; в Optuna inner score вычислялся именно по этому объекту. Качество trial и переносимый рецепт расходились.
2. Histogram callback передавал `iteration - 1`, а фильтр кривой проверял кратность интервалу. При интервале 2 точки 2/4/... превращались в 1/3/... и все пропадали. Пример с интервалом 3 и максимумом 7 теперь возвращает точки **3, 6, 7**.
3. Внутренний `schedule_selection=True` запускал native early stopping даже при уже заданных `iteration_schedule`/`frozen_iterations` или выбранном explicit checkpoint. Это могло переотбирать расписание и обращаться к ненужному holdout. Воспроизведено для четырёх boosting-семейств и обоих frozen-полей; отдельный случай — checkpoint + early stopping.

До изменений минимальный новый набор дал **11 failed**, включая явное `4 != 2` и потерянную кривую. Это проверки отдельных подтверждённых нарушений, не оценка качества на неизвестных данных.

## Исправление и стоимость

Histogram learner теперь возвращает снимок fitted estimator, который получил выбранную внутреннюю метрику. Используется `deepcopy`, без повторного обучения и без редактирования приватных массивов деревьев sklearn. Старый снимок освобождается перед созданием нового: во время histogram selection удерживаются растущий estimator и один лучший снимок. Это дополнительная память и копирование; точный peak RSS на больших данных этим этапом **не измерен**. Время копирования попадает в существующие измерения fit/общего worker времени. Тест отдельно считает реальные вызовы fit: для checkpoint 2 → stale 4 остаются ровно **два**, дополнительного fit для восстановления нет.

Возвращаемый fitted estimator сохраняется вызывающим DirectPipeline. Для остальных трёх native learners возвращается исходный объект, уже поддерживающий выбранное состояние. Если для target есть фиксированное или ранее выбранное число итераций, приоритет получает оно; новый early stopping не запускается. Публичная кривая использует число обученных раундов, начиная с 1; Optuna pruning steps остаются zero-based. Histogram записывает все свои sparse checkpoints, включая неполный последний интервал.

Документация получена через Context7 с обязательным resolve-library-id. [HistGradientBoostingRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html) и [glossary warm_start](https://scikit-learn.org/stable/glossary.html) подтверждают добавление новых итераций при повторном fit на тех же данных. Тестируемая установленная версия **scikit-learn 1.5.2**; текущая stable-страница не объявляется документацией именно этой версии.

## Проверки

Итоговый новый набор — **15 passed**. Он проверяет минимизацию RMSE и максимизацию Macro F1 с объявленным обратным порядком классов; совпадение прогнозов выбранного объекта и независимого frozen replay на тех же допустимых строках; pickle round-trip; реальный Optuna score против независимо пересчитанного RMSE; полный refit без нового create_study; frozen-приоритет у LightGBM/XGBoost/CatBoost/HGB; сохранение explicit checkpoint. Два Controller → JSON request → отдельный worker сценария реально обучают HGB и LightGBM HPO, загружают сохранённые модели и сверяют исполненное число раундов с frozen recipe/hash. Control в этих сценариях остаётся закрытым, реальных LLM calls — 0.

Расширенный набор: **71 passed / 3 failed / 1 skipped**. Все три отказа и пропуск связаны с отсутствующим AutoGluon; его пути не объявляются проверенными. Более ранний связанный набор дал 27 passed и пересекается с итоговым; счётчики не суммируются. Отрицательные и положительные XML, их SHA и final-source SHA перечислены в `research/agent_path_audit_20261026/schedule_identity.json`.

Это исправление соответствия выбора и исполнения, а не доказанный прирост RMSE/Macro F1 на задачах организаторов или автономности настоящего Qwen. Новых organizer API calls — **0**. Зависимости, main, конкурсный ZIP и чужие работающие серии не менялись. Замороженный авторский DL-эксперимент не переобучался и его результаты не переписывались. Общий goal остаётся активным; полная проверка качества, ресурсов конкурсной среды и самостоятельного выбора агента не закрыта.
