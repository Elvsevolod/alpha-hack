# Как проверять пользу изменений агента

Дата: 22 октября 2026 года. Статус: проект протокола, **ничего из перечисленных новых экспериментов не запускалось**. К этому документу относятся 46 карточек [плана](../../План_повышения_качества_агента.md). Ни наличие файла, ни его численные ориентиры не разрешают платный запуск.

## 1. Что измеряется

Главный объект — конечный `submission.csv` после завершения выбранной политики, с точной моделью происхождения и оценкой на недоступной агенту внешней проверке. Дополнительно измеряются качество лучших доступных кандидатов, выбор финалиста и цена каждой фазы. Эти величины нужны для объяснения результата, но не заменяют его.

Для задачи сохраняются разные результаты:

1. Внутренний train/inner feedback — разрешённый поиск и HPO.
2. Внешняя validation агента — в пределах фиксированной feedback policy.
3. Control агента — однократно после freeze, без возврата в исследование.
4. **Benchmark holdout верхнего уровня** — независимая оценка итогового CSV исследовательским harness после окончания попытки. Он не передаётся агенту, critic, оптимизатору промптов или runtime selector.

Benchmark holdout не заменяет control и не является ещё одним разрешённым HPO-fold. В нескольких сравниваемых попытках доступ к нему организован только у внешнего оценщика; просмотр результатов превращает задачу в dev, если по ним меняют агентную политику.

## 2. База и изоляция изменений

1. Дождаться принятой версии А/Б по действующему QA-плану. Зафиксировать, что именно включено из методической ML-политики. Сохранить source/ZIP hash и результаты собственной приёмки.
2. Для каждой идеи создать отдельный экспериментальный вариант от этой базы. Не менять одновременно модели по умолчанию, feedback, среду, лимиты и инструкции, если это не цель эксперимента.
3. Сохранить точные task/feature/metric/output contracts, train/test hashes, split/protocol hashes, корпус, pipeline, среду и ресурсы.
4. Изменения времени проверять также на одинаковом **общем** лимите. Если один вариант раньше закончил поиск и успел refit, это часть эффекта политики, не нарушение равенства.
5. Изменения HPO сначала сравнивать без LLM, затем в составе автономного агента. Первый этап показывает качество оптимизатора, второй — умеет ли Qwen правильно им пользоваться.
6. Случайность обучения фиксировать одинаковым набором seed. Детерминизм ответов Qwen не предполагать: seed модели обучения не обеспечивает одинаковую траекторию LLM. Сохранять доступные fingerprints/usage/settings и делать повторы.

Постоянные исходники сторонних проектов приведены в [SOURCES.md](SOURCES.md). Их код служит основанием идеи; прогон чужого benchmark не подменяет проверку нашего агента.

## 3. Набор задач и защита от переобучения исследователя

Две уже разобранные public-задачи соревнования использовать для разработки, воспроизведения ошибок и проверки формата. Их просмотренные control-результаты не объявлять свежими слепыми метками. Перестановка колонок проверяет устойчивость интерфейса, но не создаёт независимую ML-задачу.

Нужны отдельные dev и confirmation семьи. Для начала можно подготовить следующую матрицу; конкретные датасеты, права на использование и ограничения фиксируются до первой оценки. Внешние данные допустимы только для локального исследовательского benchmark и не попадают в конкурсный агент или его runtime-память.

| Семья | Проверяемое свойство | Как устроить независимую оценку |
|---|---|---|
| IID mixed regression | Категории, нелинейность, нормальный масштаб | Отдельный недоступный holdout без дублей между частями |
| Tail regression | RMSE и редкие крупные ошибки | Достаточная масса хвоста на holdout; исходная шкала |
| Imbalanced multiclass | Macro F1, support и decision rule | Все известные классы; отдельные объекты, не копии train |
| Text/mixed features | Выбор представления и custom | Другие источники/группы текста, сохранение разрешённых весов |
| Temporal | Смена периодов и rolling validation | Последующий период, который не выбирался по результату |
| New groups | Перенос на неизвестные сущности | Целые holdout-группы, непересекающиеся с train |
| Missingness/category shift | Работа с пропусками и неизвестными категориями | Зафиксированный сценарий сдвига, не подобранный под победителя |
| Cost/shape stress | Дорогой preprocessing, large test, multioutput | Отдельная техническая серия с контролируемыми затратами |

Для подтверждения универсальной пользы желательно несколько независимых датасетов в основных семействах. Восемь задач по одной на семейство дают лишь ограниченный пилот; три seed не превращают их в 24 независимых датасета. Производные одного исходного датасета объединяются в один статистический кластер.

Отдельные синтетические fixtures допустимы для знания правильного инварианта: недопустимая утечка, неправильный знак метрики, шесть точек сетки, потеря индекса, исчерпание бюджета. Их простота не позволяет судить о качестве на реальных сложных данных.

## 4. Лестница проверки

### L0. Детерминированная техническая проверка — без Qwen

Проверить связанные с изменением контракты и только необходимые регрессии. Не переписывать весь набор тестов под каждый обратимый документарный вариант. Сохранить доказательства для:

- Границ данных, row/class alignment, метрики и схемы результата.
- Перспективного резерва нового лидера и ансамбля, нерасходуемого refit, общего дедлайна и восстановления.
- Реального sampler/startup, уникальности grid trials, продолжения study, frozen refit без HPO.
- Сопоставимости parent/delta, версий источников, отсутствия выдуманной применимости.
- Прежнего безопасного CSV при отказе новой фазы.

Для времени нужны как контролируемые часы/стоимости для точных границ, так и настоящее время/точная среда. Трёхчасовая нагрузочная репетиция из QA остаётся обязательной там, где затронуто завершение; короткий unit-тест её не заменяет.

Переход дальше: все обязательные инварианты проходят. Это технический verdict, не доказательство прироста ML-score.

### L1. Replay решений — Qwen только после отдельного согласования

Подготовить, например, 24 состояния с балансом: ошибка инструмента, неопределённый результат, плохой перенос, редкий класс, хвост, новая гипотеза, HPO-budget, близость к refit, чтение/stale evidence, сжатие и рестарт. Использовать состояния из разрешённого журнала до открытия control плюс новые независимые fixtures.

Сравнение двух вариантов с двумя повторениями даёт **96 ответов**. Это ориентир состава, не утверждение о достаточной статистической мощности и не уже согласованный расход.

Оценщик проверяет:

- Допустимость команды и неизменность постановки.
- Корректное понимание измеренного результата и неопределённости.
- Отсутствие повтора того же вычисления без причины.
- Совместимость действия с оставшимся временем и модельным интерфейсом.
- Точные версии/типы evidence и разумный способ получить недостающие данные.

Допустимых следующих действий может быть несколько. Нельзя наказывать хорошую альтернативу за несовпадение с единственной эталонной строкой. По replay нельзя утверждать, что новый policy даёт лучший полный ML-результат: продолжение траектории ещё не выполнено, а распределение состояний от другой политики может быть иным.

### L2. Offline HPO и политики затрат — без Qwen

Для HP01/HP02/HP03/HP05/HP07/HP08 использовать один исполнимый pipeline, те же fit/inner splits и общую целевую метрику. Отдельные факторы:

| Фактор | Варианты | Что зафиксировать |
|---|---|---|
| Sampler | random, нынешний TPE, TPE с подходящим startup, малый grid | Одинаковые пространство, время и допустимые конфигурации |
| Study | Новый каждый раз / продолжение | Тот же совокупный ресурс и совместимые fingerprints |
| Trial admission | Только timeout / оценка next trial + selected fit | Резерв публикации и общий дедлайн |
| Fidelity | Full / измеренная предварительная ступень | Независимое подтверждение full-конфигурации |
| Проверка shortlist | Один split / заранее заданные внутренние folds | Протокол времени/групп и полный pipeline |

Для первого отсечения достаточно небольшого dev-пилота, например 4 задачи × 3 стратегии × 2 seed × 15 минут = **6 часов** совокупного времени попыток. Все варианты одновременно не обязательны: сначала устранять несогласованность startup и бюджета, затем расширять сравнение. Время HPO включает выбранный fit, прогноз и запись. Число trials не считается равным бюджетом, если их стоимость отличается.

Для TM02 можно сначала воспроизводить прогнозы по сохранённым прошлым измерениям: в момент предсказания разрешены только более ранние фазы этой истории. Оценка ошибки прогноза не использует будущее как вход.

### L3. Короткие автономные dev-запуски

После L0/L1/L2 оставлять только перспективные блоки. Пример одной пары вариантов: 4 dev-задачи × 2 варианта × 2 повтора × 30 минут = **8 часов** времени попыток. Четыре такие идеи отдельно — уже 32 часа. Не запускать все 46 вариантов подряд.

В этой фазе отсекаются неработающие решения и грубые регрессии. Положительный короткий результат не переносится автоматически на три часа: доля reasoning, зрелость HPO, число гипотез и стоимость refit меняются с горизонтом.

Общую baseline-серию разрешается переиспользовать только в заранее определённой волне при неизменных данных, среде и правилах. Изменение состояния API/нагрузки/инфраструктуры требует учёта или нового сравнения; вчерашний быстрый baseline не доказывает экономию сегодняшнего варианта.

### L4. Подтверждение в полном горизонте

Заранее выбрать один или очень небольшой пакет победивших dev-блоков и свежие confirmation-семьи. Сохранить решение и пороги до просмотра новых результатов.

Пример полного сравнения: 8 задач × 2 варианта × 3 повтора × 3 часа = **144 часа** совокупного времени попыток. Это существенный объём. Он показывает цену надёжного вывода; не является предложением потратить ресурс автоматически. Фактические CPU-часы зависят от выделения CPU, API-расход — от measured usage, а не от этого арифметического числа.

Если доступен только меньший пилот, дать результат с широкой неопределённостью. Не уменьшать число задач незаметно и не заменять независимые задачи дополнительными seed на одной public-постановке.

Варианты запускать в перемешанном/сбалансированном порядке, чтобы дрейф сервиса и общая очередь не совпали с одним arm. Параллельные задачи — только при проверенной совокупной мощности. Время ожидания общего шлюза учитывать отдельно, а для пользовательского срока — полностью.

### L5. Проверка вклада и взаимодействий

Для минимального принятого пакета убрать по одному компоненту и повторить сопоставимое dev/confirmation сравнение, заранее определив новый набор или ограничив вывод исследовательским. Отдельные взаимодействия:

- TM01–TM04 × HP01/HP04: больше HPO не должно лишать full refit.
- AQ12 × AQ02/AQ03: диагностика бесполезна, если её не удаётся превратить в эксперимент.
- AQ21 × AQ22: экономия контекста/рассуждения не должна ухудшать сложные решения.
- AQ14 × AQ25: дополнительный ансамбль и shortlist должны помещаться в полный граф.

Одна успешная комбинация не доказывает пользу каждого её компонента. Если блок полезен только во взаимодействии, так и записать.

## 5. Метрики и их смысл

### Конечное качество

Для каждой задачи/повтора хранить исходные RMSE, Macro F1 либо её подтверждённую основную метрику без округления, и signed delta с правильным направлением. Accuracy не заменяет Macro F1. Фиксировать выходной scope: fit, control_prepared, full_train_refit, технический fallback.

Для сводки разных задач допустим заранее выбранный показатель относительного уменьшения ошибки:

`q_d = (error_base_d − error_variant_d) / max(error_base_d, epsilon_d)`

Здесь для RMSE ошибка = RMSE, для F1 — `1 − F1`. `epsilon_d` и способ усреднения фиксируются до результатов; задачи с почти нулевой ошибкой требуют отдельного разбора. Это исследовательская нормировка, **не формула официального score**. Публиковать также все сырые дельты и раздельные сводки regression/classification/temporal/group; среднее не должно скрывать тяжёлую регрессию одной семьи.

Если baseline сам стохастичен, сравнивать соответствующие повторные попытки либо заранее выбранные средние, не нормировать каждый вариант на лучший удачный baseline seed.

### Завершение и надёжность

- Доля попыток с валидным CSV, completed control и completed full refit.
- Доля результата `full_train_refit`, а не просто state=completed.
- Частота timeout/OOM/invalid command/неизвестного исхода, отдельно от плохого ML-score.
- Падение качества от лучшего допустимого кандидата до реально опубликованного результата.
- Неиспользованное время и недооценка стоимости фаз.

Если итоговый CSV валиден, оценивать именно его, даже при fallback. Невалидный/отсутствующий CSV не исключать из среднего успешных. Показать coverage и консервативный составной результат; для ограниченных метрик заранее можно задать худшее значение, а для неограниченной RMSE отсутствие результата учитывать отдельным провалом и анализом чувствительности, не придумывая удобную конечную ошибку.

### Эффективность и диагностика

- Wall-clock до первого обученного CSV и до законченного результата.
- Время Qwen, очередь, чтение/контекст, worker, финализация; без двойного счёта пересекающихся интервалов.
- Реальные API units/usage и токены отдельно: units организаторов не называть долларами.
- Полезные completed full experiments на час и на API unit.
- Доля правильного восстановления команды, повторов и неприменённых гипотез.
- Best-validation curve и конечная holdout-метрика. Рост первой при стагнации второй — сигнал переотбора.

Количество токенов, число моделей, глубина дерева, чтения справочника и красивые explanations — промежуточные показатели. Сами по себе они не свидетельствуют о пользе.

## 6. Предлагаемые правила принятия: зафиксировать до серий

Ниже **инженерные стартовые допуски**, не научно установленные универсальные константы. Их можно изменить до регистрации серии с объяснением цены ошибки; после просмотра результата — только новая серия/статус dev.

### Общий технический барьер

Нет новых нарушений контракта данных/метрики/публикации/дедлайна; все адресные проверки проходят. Сбой трактуется по происхождению. Сохранённый fallback не считается успешно выполненным full refit.

### Q-gate: прирост качества

На свежих confirmation-семьях средняя заранее выбранная нормированная дельта положительна, а нижняя граница 95% интервала выше нуля. Интервал строить с ресемплированием **задач/семей**, сохраняя зависимость seed и производных данных; при малом числе кластеров явно показывать ненадёжность интервала. Не считать строки holdout независимыми копиями всей агентной попытки.

Дополнительно проверить раздельные семьи и full-refit coverage. Предлагаемый предел допустимого ухудшения для экономичного варианта: 1% RMSE и 0,003 абсолютного Macro F1 в соответствующей сводке. Для доказательства «не хуже» нужен non-inferiority анализ, а не незначимый p-value обычного теста. При широком интервале вывод — неопределённо.

### E-gate: экономия без существенного ущерба

Заранее выбрать основной ресурс: API units либо время до сопоставимого готового результата. Стартовый ориентир — не менее 15% экономии, с интервалом, поддерживающим реальную экономию, при выполненном non-inferiority по качеству и отсутствии потери надёжности. Проверять не только среднее, но и медленный хвост. Уменьшение calls без уменьшения времени/стоимости не считается самостоятельной победой.

### R-gate: более надёжный законченный результат

Для TM-изменений обязательны успешные контролируемые случаи, где старый вариант теряет refit. Затем в полных попытках сравнить долю `full_train_refit`, число недооценок и конечное качество с учётом failures. Предложение можно принять как техническую защиту при подтверждённом устранении дефекта, но это не доказывает роста предсказательной метрики. Для общего включения требуется также отсутствие недопустимого ухудшения по Q/E-критериям.

### Пороги расследования и отката

Потеря CSV, утечка, подмена метрики и нарушение control-фазы блокируют включение. Ухудшение отдельной задачи примерно более 5% RMSE или 0,02 Macro F1 — повод остановить продвижение варианта и разобрать причину; это не автоматическое доказательство общей статистической непригодности по одному seed. Новый платный повтор не запускается автоматически.

Исходы по идее: **принять**, **принять только для указанного режима**, **отклонить**, **неопределённо**. Отсутствие статистического доказательства вреда не означает доказанную пользу.

## 7. Прямые проверки времени

| Сценарий | Должно произойти |
|---|---|
| Новый кандидат дорогой, старый лидер дешёвый | Допуск учитывает его условный полный граф до большого fit |
| Pilot выявил более дорогой preprocessing | Бюджет пересчитан до full candidate; Qwen получает причину |
| Контроль помещается, full refit не помещается | Нет ветви, расходующей защищённый refit без явного решения заранее |
| Предыдущий финалист оказался медленнее | Новый остаток и refit защищены перед следующим worker |
| Два ансамбля имеют общую модель | Общая зависимость считается и готовится один раз |
| Большой test, быстрый fit | Predict/save/write получают реальный резерв |
| HPO завершил хороший trial, следующий слишком дорогой | Поиск заканчивается, выполняется selected fit и сохранение |
| Долгий API-вызов/очередь около границы | Отсутствует новый запрос после обязательного freeze; deadline не продлён |
| Рестарт в frozen/control/refitting | Исследование не возобновляется; подтверждённое вычисление не повторяется |
| Refit не удался | Сохранён пригодный предыдущий CSV; статус не маскируется |

Не обещать гарантированное завершение произвольного неизвестного custom fit по оценке времени. Цель — измеряемое снижение недооценок и защищённая деградация, с внешним жёстким дедлайном.

## 8. Прямые проверки HPO

1. В pinned Optuna 4.2.1 проверить фактический random startup до 10 trials; default-вызов на 8 попыток не описывать как уже адаптивный TPE.
2. Сравнить короткие random/TPE режимы на одинаковом пространстве. Число адаптивных предложений сохранять отдельно от общего числа попыток.
3. Для 2×3 сетки получить шесть уникальных допустимых конфигураций либо явный budget-limited статус. Изменение параметра quantization не должно молча менять сетку.
4. Повторно открыть совместимый study: старые completed trials не исполняются заново; неизвестный outcome требует восстановления.
5. Изменение split/preprocessing/metric/data/fidelity не смешивает старые и новые scores.
6. Выбранная конфигурация refit не вызывает optimize/AutoML-selection ещё раз.
7. AutoGluon `n_trials` текущего адаптера считать ограничением списка learners; полноту настоящего HPO доказывать разными параметрами в журнале.
8. Pruning подтверждается вызовами корректных intermediate reports и измеренной экономией; одного слова pruning в инструкции недостаточно.

## 9. Расходы и авторизация

Новые реальные серии требуют отдельного согласования бюджета по действующему QA-плану. Старый предел 180 units не переносится автоматически. До серии/после завершения, ошибки или отмены применяется `alpha-api-limits`; отдельные before/after сохраняются в её каталоге. Секреты и полный `/key/info` не включаются в отчёт. При ошибке проверки остаток неизвестен.

Начальную оценку бюджета строить по фактическому preflight/сохранённому usage: число ответов × наблюдённая цена с запасом; серверная задержка учёта и сторонние процессы отражаются отдельно. Не выдумывать стоимость будущих 96 ответов или 144 часов по чужой цене токена.

Поскольку пользователь попросил сейчас только план, ни локальные новые сравнения, ни Qwen-серии, ни правки runtime не выполняются этим заданием.

## 10. Запись результата одной идеи

Минимальный пакет будущего эксперимента:

- `PREREGISTRATION`: идея, base/variant, единственный фактор, задачи/семьи/seed, ограничения, пороги и правило остановки.
- `MANIFEST`: хеши кода, данных, корпуса, среды, ресурсов и внешнего протокола.
- `RUNS`: все начатые попытки, включая failures/cancelled/unknown, связь результатов и бюджетов.
- `RESULTS`: сырые метрики, CSV provenance, control/refit, timings, usage и predeclared сводки/интервалы.
- `DECISION`: принять/ограничить/отклонить/неопределённо, ограничения переносимости, точный откат и следующий разрешённый шаг.

Форматы имён здесь предложены для будущей реализации, а не объявлены существующими API. После принятия пакета выполнить архивные проверки через `alpha-submission-zip`; это отдельная работа. Отправка на платформу остаётся отдельным действием.
