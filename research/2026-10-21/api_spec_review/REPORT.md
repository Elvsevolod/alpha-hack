# Спецификация API и текущая реализация v009

Проверено 21.10.2026. Изучены опубликованная OpenAPI-схема прокси организаторов, доступные нашему локальному ключу метаданные, официальные сведения Qwen/OpenRouter и содержимое архивов v008/v009. Запросы генерации не выполнялись. Восемь выбранных технических проверок v009 прошли на имитации API. Исходники агента и настройки подключения не изменялись.

На сайте ключ предоставляется внешним окружением организаторов. Локальный `.env` используется для разработки; он не является источником ключа на платформе и не включён в ZIP. Прочитанные локальным ключом квоты и список моделей относятся к этому ключу и этому адресу на момент проверки. Они не устанавливают настройки окружения, которое организаторы выдадут при оценке решения.

**Какая версия изучена.** Новейший собранный кандидат — `dist/solution_v009.zip`. Все 25 встроенных Python-файлов проекта совпадают с текущими исходниками. `dist/CANDIDATE.json` указывает на v009, а `dist/LATEST.json` сохраняет указатель на локальную приёмку v008. Полные публичные прогоны окончательного v009 с Qwen не завершены; архив пока не объявлен готовым к загрузке. Исторический набор из 155 технических тестов записан в свидетельстве приёмки v009, восемь относящихся к этому исследованию проверок выполнены повторно.

**Сервис и формат запросов.** По [опубликованной схеме](https://changellenge.up.railway.app/openapi.json) текущий внешний сервис — LiteLLM API 1.105.1. Наш клиент использует `POST /v1/chat/completions`, JSON и заголовок `Authorization: Bearer <ключ из окружения>`. Обязательные поля тела — `model` и `messages`. LiteLLM переводит запрос к провайдеру; доступные нашему локальному ключу метаданные называют OpenRouter. Цепочка текущего локального подключения: агент → прокси организаторов → OpenRouter → сервер Qwen. Конкретный конечный сервер не установлен.

Схема также перечисляет другие маршруты, включая Responses, embeddings и административные операции. Их наличие в общей OpenAPI-схеме не устанавливает доступ нашего ключа или среды соревнования. Агент пользуется только Chat Completions. При исследовании `GET /v1/models`, `GET /model_group/info` и чтение информации о собственном ключе были доступны; `/utils/supported_openai_params` вернул HTTP 401. Обход этого ограничения не выполнялся.

**Подключение на платформе.** `solution.py:15` загружает необязательный локальный `.env` с `override=False`. Затем `automl_agent/qwen.py:81–87` читает окружение. Внешние значения организаторов имеют приоритет. В ZIP находятся только `solution.py`, `agent_bundle.py`, `requirements.txt`, поэтому локальный `.env` вместе с ключом и дополнительными настройками в поставку не переносится.

| Настройка | Что делает | Текущее состояние |
|---|---|---|
| `OPENAI_API_KEY` | Авторизация запроса | На сайте поступает из внешнего окружения организаторов; в коде значения ключа нет |
| `OPENAI_BASE_URL` | Адрес API, к которому добавляется `/chat/completions` | Читается из окружения; v009 поддерживает HTTP и HTTPS, в том числе внутренний адрес runner |
| `OPENAI_MODEL` | Идентификатор запрашиваемой модели | Необязателен; при отсутствии или пустом значении используется `qwen/qwen3.8-27b`. Выбор ограничен тем, что разрешает выданный ключ и сервер |
| `AGENT_CONTEXT_TOKENS` | Локальная защита от переполнения контекста | По умолчанию 262144; изменение не увеличивает возможности сервера |
| `AGENT_OUTPUT_TOKENS` | Начальное значение отправляемого `max_tokens` | По умолчанию 8192; v009 при обрезании ответа увеличивает его, для стандартного старта — до 16384, затем 32768 |
| `OPENAI_EXTRA_BODY` | Дополнительные поля тела запроса | По умолчанию `{}`; локально заданы `temperature=0.2` и `reasoning.enabled=false` |
| `--transport` | Выбор native tools или JSON-команды | По умолчанию `auto`; доступны также `native` и `json` |

`--transport native` в текущем коде также допускает переход к JSON после ошибки формата или неподдерживаемого запроса: это не строгий запрет резервного транспорта. Сохранённый в журнале транспорт имеет приоритет при восстановлении запуска.

**Параметры генерации.** В содержимом `OPENAI_EXTRA_BODY` поля задаются напрямую, например `{"temperature":0.2,"reasoning":{"enabled":false}}`. Клиент разворачивает этот объект в верхний уровень HTTP JSON; отдельное поле `extra_body` серверу для этого не нужно. Общий механизм передачи дополнительных полей уже реализован. По [документации LiteLLM](https://docs.litellm.ai/docs/completion/provider_specific_params), параметры провайдера могут передаваться дальше; это не гарантия, что выбранный конечный сервер применит каждое поле.

| Параметр | Возможность API | Что делает v009 |
|---|---|---|
| `temperature` | Управляет разнообразием генерации | Передаётся через дополнительные поля; локально 0.2, при отсутствии настройки не задаётся |
| `top_p` | Ограничивает суммарную вероятность выбираемых токенов | Можно передать через дополнительные поля; сейчас явно не задан |
| `top_k`, `min_p` | Дополнительное ограничение выбора токенов | Можно передать; поддержка зависит от конечного сервера, сейчас не заданы |
| `reasoning`, `reasoning_effort` | Управляют режимом и глубиной reasoning при поддержке маршрутом | Можно передать; локально отправляется `reasoning.enabled=false`; автоматического выбора глубины по шагам нет |
| `frequency_penalty`, `presence_penalty`, `repetition_penalty` | Управляют повторениями | Можно передать; сейчас не заданы, поддержка зависит от сервера |
| `seed` | Управление случайностью генерации при поддержке сервером | Можно передать; сейчас LLM-seed не задан. Аргумент агента `--seed` задаёт seed обучения, а не этот API-параметр |
| `stop` | Останавливает генерацию по указанной последовательности | Можно передать; сейчас не задан |
| `response_format` | JSON-режим или структурированный вывод при поддержке маршрутом | Можно передать; штатный JSON-транспорт сейчас использует инструкции, схемы в сообщении и проверку ответа, без запроса серверного `response_format` |
| `logprobs`, `top_logprobs` | Вероятностная диагностика ответа при поддержке сервером | Их можно запросить, но текущий клиент не сохраняет и не использует эти дополнительные результаты |
| `tools` | Схемы вызываемых функций | Формируются из девяти внутренних типизированных инструментов, через окружение не заменяются |
| `tool_choice` | Управление выбором инструмента | В native-запросе принудительно `required` |
| `parallel_tool_calls` | Несколько вызовов инструментов за ответ | Принудительно `false`; контроллер выполняет одну операцию за шаг |
| `stream` | Потоковая выдача | Принудительно `false`; обработчика потока нет |
| `n` | Количество вариантов ответа | Клиент ожидает ровно один `choice`; установка `n>1` через дополнительные поля несовместима с его текущим разбором |

Клиент запрещает задавать в дополнительных полях `model`, `messages`, `tools`, `stream`, `max_tokens`, `tool_choice`, `parallel_tool_calls`. Для модели, адреса и размера ответа есть отдельные настройки. `max_completion_tokens` не запрещён этим списком, но он способен конфликтовать с уже отправляемым `max_tokens`; текущий предусмотренный путь настройки длины — `AGENT_OUTPUT_TOKENS`.

В [официальной карточке Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) описаны thinking/non-thinking и уровни `reasoning_effort`: `xhigh`, `medium`, `low`. Рекомендации автора для sampling отличаются от нашего локального `temperature=0.2`: thinking — temperature 1.0, top_p 0.95; non-thinking — temperature 0.7, top_p 0.8. Это рекомендации автора модели, а не доказательство оптимальных настроек для наших ML-задач. Формат управления thinking зависит от сервиса: у OpenRouter используется объект `reasoning`, у собственного сервера Qwen могут быть другие поля. Менять формат без проверки маршрута оснований нет.

**Важное различие локального запуска и сайта.** Сейчас локальный `.env` задаёт:

```json
{
  "temperature": 0.2,
  "reasoning": {"enabled": false}
}
```

Если организаторы передадут только необходимые параметры подключения и не зададут `OPENAI_EXTRA_BODY`, архив v009 отправит запрос без явной температуры и без явного переключателя reasoning. По исходникам невозможно установить фактический режим reasoning на сайте: он зависит от внешнего окружения и настроек сервера. Утверждение «в v009 на сайте reasoning отключён» поэтому не подтверждено. Подтверждено только наличие такой настройки в локальном `.env` и её передача нашим клиентом.

У reasoning и обычного ответа часто общий лимит выходных токенов; при исчерпании лимита возможен `finish_reason=length` с пустым окончательным ответом. Это описано в [документации OpenRouter](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens). Отсюда практическая связь между режимом reasoning и размером `AGENT_OUTPUT_TOKENS`. Поле `reasoning.exclude=true` скрывает reasoning из ответа, но не равнозначно его отключению. Наш клиент отдельно `reasoning_tokens` не учитывает и `reasoning_details` между шагами не переносит; он сохраняет суммарные `prompt_tokens`, `completion_tokens`, `total_tokens`.

**Контекст и противоречия метаданных.** Прокси сообщает для модели `max_input_tokens=1000000`, `max_output_tokens=1000000`, но одновременно возвращает `supports_function_calling=false`, `supports_reasoning=false` и `supported_openai_params=null`. Эти поля не дают надёжного описания реально доступного режима: [публичный каталог конечных серверов OpenRouter](https://openrouter.ai/api/v1/models/qwen/qwen3.8-27b/endpoints) перечисляет поддержку tools и reasoning, а исторические локальные прогоны через этот прокси подтверждали вызовы инструментов. При этом новый запрос генерации для проверки reasoning в данном исследовании не делался.

В сохранённом каталоге OpenRouter 20 маршрутов; заявленные окна контекста составляют 65536, 262144 или 1000000, ограничения ответа — от 32768 до 262144 токенов. Фактический маршрут организаторов не установлен. Поэтому значения «миллион на вход/выход» нельзя считать гарантией нашего подключения. В агенте остаётся собственный предел 262144 и консервативная оценка размера запроса по UTF-8-байтам с резервом ответа. Токенизатор Qwen для точного измерения входного контекста не используется.

**Что изменилось именно в v009.** Сравнение выполнено с кодом, извлечённым из обоих ZIP, без исполнения содержимого архивов.

- HTTP/HTTPS-адрес runner принимается из окружения; учитываются стандартные настройки сетевого прокси окружения.
- Один запрос имеет общий предел до 300 секунд, соединение — до 15 секунд. Фактическое доступное время уменьшается с учётом дедлайна задачи и резерва финализации. Эти значения не вынесены в отдельные CLI/env-настройки.
- HTTP 401/402/403 выделены как недоступность доступа или бюджета; временные 408/409/429, 5xx, ошибки соединения и обрезание ответа не переключают native tools в JSON сами по себе.
- Обрезание ответа увеличивает записанный лимит следующего ответа. Увеличение сохраняется при восстановлении запуска; ручное уменьшение env-значения не уменьшает уже сохранённое большее значение этого запуска.
- При нескольких native tool calls выполняется первый, остальные не исполняются в этом шаге; журнал фиксирует событие.
- После трёх временных сбоев исследование не прекращается автоматически: есть восстановительные ML-эксперименты и паузы между повторными попытками до 30 секунд.
- Убраны стандартные ограничения 32 обращения, 12 кандидатов и отдельные 1200 секунд LLM. `--max-calls` и `--max-candidates` остаются явными ограничениями для разработки. По умолчанию действует общий срок до 175 минут с резервом завершения; это локальная политика агента, а не отмена серверных квот.
- При увеличении состояния сокращается подробность старой обратной связи. Журнал остаётся источником состояния; каждый API-шаг получает заново собранные system/user сообщения, а не полную стандартную последовательность assistant/tool сообщений.

**Какие ограничения задаёт сервер.** Для локального ключа сейчас разрешена одна модель `qwen/qwen3.8-27b`; его запись содержит `max_budget=600`, период `1d`, а RPM/TPM и число параллельных запросов не заданы. `null` в записи ключа не исключает ограничений команды, сервера и конечного провайдера. Эти сведения не распространяются автоматически на ключ, выдаваемый при проверке сайта. Клиент не управляет серверной квотой, весами модели, расширением её контекста или разрешённым списком моделей.

**Что остаётся не реализовано или не проверено.** Нет отдельного профиля генерации, встроенного как одинаковые значения по умолчанию для локального и платформенного запуска; нет автоматического выбора reasoning по типу шага; нет потокового клиента; нет отдельной статистики reasoning-токенов; резервный JSON-транспорт не запрашивает принудительный JSON Schema у сервера. Документация и метаданные подтверждают варианты конфигурации, но применение всех дополнительных параметров именно маршрутом организаторов в этом исследовании не измерялось.

Первый полезный шаг перед следующим разрешённым живым испытанием — выбрать и явно зафиксировать профиль генерации для платформы, сохранив обязательное чтение ключа и адреса из внешнего окружения. Затем коротко проверить применение reasoning и structured output на фактическом адресе; после этого сравнивать качество профилей на одинаковых задачах. Из данного исследования не следует, что включение reasoning само по себе улучшит метрики ML-решения или объяснит нулевую оценку v008.
