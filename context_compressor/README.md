# Отдельный модуль сжатия контекста

Реализация плана «идем по правильному сжатию контекста.md» от 21.10.2026. Модуль находится отдельно от `automl_agent`, не импортирует его, не меняет основной цикл и не обращается к API. Для работы достаточно стандартной библиотеки Python 3.11+; целевая среда проекта — Python 3.12.

Сжатие выполняется по правилам. Полные разрешённые данные остаются в SQLite, рабочее состояние хранится отдельно, запрос собирается из ограниченного снимка. Дополнительная модель и установка зависимостей не нужны.

## Подключение к основному агенту

21.10.2026 модуль подключён через `automl_agent/context_memory.py`. Штатный исследовательский цикл использует его снимки и точные тела запросов; прежний `Controller.context()` сохранён как диагностическое представление. Команды, исследовательские заметки и подтверждения доставки устойчивы к перезапуску. Результат операции и очередь наблюдений фиксируются общей транзакцией в `journal.sqlite`, а неизвестный исход не запускается повторно вслепую.

Маршруты `analyze_experiments.context_read` и `context_search` работают через тот же контроллер. Сжатие сохраняет полный контракт, исходную область и доверие фрагментов, резерв завершения и счётчики. В плоской поставке собственные модули сжимателя входят во встроенный runtime; новые сторонние зависимости не добавлены. Отдельный архив v001 и прежние отчёты ниже описывают состояние до интеграции.

Актуальная поставка — v016: `../outputs/context_savings_v016/REPORT.md`. На прежних историях подтверждена экономия входных токенов полного запроса и наличие 20 выбранных фактов в обеих задачах. В короткой проверке Qwen все значения верны, но один ответ нарушил схему имён JSON-полей. Предыдущая интеграция описана в `../outputs/context_integration_v014/REVIEW_AND_TESTS.md`. Эти проверки не заменяют полную приёмку качества из `ACCEPTANCE_PROTOCOL.json`.

## Проверка

Из корня проекта:

```sh
python3 -m context_compressor.verify --benchmark --output context_compressor/reports/local
```

Без замеров производительности:

```sh
.venv/bin/python -m context_compressor.verify --output context_compressor/reports/local312
```

Основной набор использует `unittest`. Дополнительная проверка экспортированных JSON Schema использует `jsonschema`, а измерение RSS — `psutil`; обе библиотеки входят в список организаторов. Если их нет в проверочной среде, это явно отражается в отчёте. Исполняемому модулю они не нужны. В сохранённой проверке Python 3.11 выполнены все 63 теста, включая проверку схем; Python 3.12 отдельно проверен с одним пропуском из-за отсутствующего локального `jsonschema`.

Результаты: `reports/python311/verification.json`, `reports/python312/verification.json` и журналы `unit-tests.txt`. Краткий итог находится в `reports/SUMMARY.md`. Замеры на текущем macOS предварительные: профиль 4 CPU / 10 ГБ принудительно не установлен. Фикстуры схем сняты с незавершённой разработки, их происхождение и хеши сохранены в `tests/fixtures/SOURCE_MANIFEST.json`.

## Интерфейс для будущего подключения

| Вызов | Назначение |
|---|---|
| `ContextStore(path, allowed_scopes=...)` | Отдельный устойчивый журнал разрешённых данных и доставки. |
| `configure(store, ...)` | Публикация подтверждённого состояния контроллером, полных TaskSpec и политик. |
| `ProfileCache(store).get_or_create(ProfileKey(...), calculate)` | Один расчёт профиля на ключ версии данных, fit-разбиения, области и формата. |
| `store.complete_operation(id, version, result, emissions, records=...)` | Одна транзакция результата, наблюдений и необязательного индекса экспериментов. |
| `compressor.snapshot()` | Один согласованный, неизменяемый снимок решения. |
| `compressor.preflight(snapshot)` | Проверка минимального запроса в обоих транспортах. |
| `compressor.prepare(snapshot, mode)` | До четырёх попыток подгонки, обновление остатка времени и сохранение точного тела запроса. |
| `compressor.accept_response(request_id, response, validate)` | Проверка ответа и атомарная регистрация команды, заметки и подтверждений доставки. |
| `store.pending_commands()` | Восстановление зарегистрированных команд, для которых ещё нет результата. |
| `store.handle_read(arguments)` | Разрешённое чтение и структурированный поиск через ветвь `analyze_experiments`. |
| `store.channel_error(...)`, `store.record_usage(...)` | Отдельная диагностика канала и серверная статистика каждого обращения, включая повторы. |

`configure` принимает `run_id`, полный подтверждённый `task` в виде JSON-словаря, `policies`, компактные `policy_flags`, `data_hash`, `protocol_hash`, `environment_hash`, исходный `deadline_epoch`, `reserve_seconds`, `cpu`, `memory_mib`, `counters`, `work` и необязательную ссылку `profile` из кэша. Обязательные признаки доступа перечислены в `REQUIRED_FLAGS`; дополнительные условия передаются ограниченными кодами со ссылкой на точные политики. Непредставимое обязательное условие отклоняется с диагностикой. Дедлайн, идентичность запуска и счётчики не сбрасываются при повторной конфигурации.

Необязательный `budget_state` — подтверждённый контроллером JSON-словарь до 1024 UTF-8 bytes. Он сохраняется как `policies_resources.budget` в защищённом core и не удаляется стадиями сжатия. AutoML передаёт локальные лимиты обращений/кандидатов/LLM-времени, остаток на момент снимка и после одной генерации, а также условную стоимость проверки гипотезы. `null` означает отсутствие локально настроенного предела, а не подтверждённую неограниченность провайдера. Это часть неизменяемого снимка: повторные transport requests могут расходовать дополнительные обращения; при них автоматически обновляется только `remaining_seconds`. Новый decision snapshot получает актуальные счётчики/лимиты из того же Budget.

`work` содержит ID опоры, лидера, последнего и активного эксперимента, операции, родителя, связанной неудачи, до восьми связанных ID и зависимостей, а также краткую диагностику до 512 UTF-8-байт. Ограниченные проекции гипотезы и отклонённых операций также сохраняются в ядре; полные источники доступны отдельно. Активные гипотеза и `research_note` имеют происхождение `agent_assumption`; ожидаемое свидетельство не становится измеренным результатом. Вопрос и предположения переносятся в соответствующие поля `ResearchState` с этой отметкой.

### Новое наблюдение

```python
from context_compressor import Source, Emission

source = Source("reference-42", "library-version-1", permitted_text,
                scope="reference", origin="offline_reference")
store.complete_operation(operation_id, "result-v1", permitted_result,
                         [Emission(source, kind="reference")])
```

Для обучения передаётся компактная карточка результата, для отладки — отдельные источники кода и диагностики. **`result` и все источники должны быть уже разрешёнными представлениями.** Модуль не определяет самостоятельно, какие поля исходного результата исполнителя можно показывать модели, и не очищает сырые данные от секретов или скрытых меток.

Результат и ожидающее наблюдение сохраняются одной транзакцией. Восстановление из уже сохранённого результата выполняется тем же вызовом с теми же ID и версиями, без повторного запуска инструмента. Изменённый результат требует новой версии; изменённая запись индекса — нового ID.

### Повторное чтение старого источника

```python
from context_compressor import SourceSlice

page = store.handle_read(command_arguments)
store.complete_operation(operation_id, "result-v1", page,
                         [SourceSlice.from_fragment(page, kind="code")])
```

Этот путь сохраняет исходные ID, версию, область и происхождение. Он читает только нужную порцию, проверяет её хеш и не загружает весь старый документ. `Emission` и `SourceSlice` используют **UTF-8-байтовые диапазоны**. Порция содержит отдельные признаки завершённости запрошенного диапазона и полного документа, хеши и маршрут продолжения.

### Отправка и принятие решения

```python
snapshot = compressor.snapshot()
compressor.preflight(snapshot, budget=131072)
prepared = compressor.prepare(snapshot, "native", budget=131072)

# Существующий клиент отправляет именно prepared.wire_json.
# Каждое новое фактическое обращение получает отдельный request_id.
command = compressor.accept_response(prepared.request_id, provider_response,
                                     validate=controller_schema_and_admissibility_check)
```

Обязательный `validate(Command)` проверяет аргументы по схеме соответствующего инструмента и допустимость действия по полному текущему контракту, политикам и ресурсам. Он поднимает исключение при отказе и не исполняет команду. Для новых маршрутов используются расширенные схемы `Transport.schemas`. Проверка выполняется внутри транзакции регистрации; вложенные записи в этот журнал из callback запрещены. Повтор уже зарегистрированной идентичной команды возвращает прежнее решение. Ответ на устаревшую идентичность задачи, протокола, среды или политики не подтверждает доставку.

Тело запроса отправляется без изменения сообщений, схем и резерва. Для повторной попытки или смены транспорта снова вызывается `prepare` на том же снимке с новым request_id; остаток времени обновляется. После фактического отказа провайдера по размеру можно указать `minimum_stage`, не меняя счётчиков исследования. После принятия команды требуется новый снимок.

**При интеграции нельзя сначала записать результат в основной журнал, а потом независимо добавить наблюдение в другой транзакции.** `complete_operation` должен стать общей точкой устойчивого сохранения разрешённого результата, его индекса и очереди. Основной контроллер может хранить ссылку на эту запись. Существующую идемпотентность исполнения и восстановление неизвестного исхода нужно сохранить: сам модуль не выполняет обучение или другие внешние действия и не доказывает однократность их побочных эффектов. Один журнал принадлежит одному запуску контроллера.

## Что сохраняется при сокращении

- Ядро до 16 384 UTF-8-байт с отдельными пределами блоков. Длинные роли, классы, выходные столбцы, веса метрики и доказательства остаются в полном контракте и разделах чтения. Исполнитель продолжает применять полный контракт.
- Активная заметка: три поля по 512 UTF-8-байт, до восьми ID по 96 байт, не более 3072 байт вместе с происхождением. Превышение отклоняется. Отсутствие новой заметки сохраняет прежнюю; закрытие задаётся явно, старые записи доступны через каталог.
- Наблюдения: отдельные 8192 байта на порцию очереди, до четырёх элементов. Новейшее наблюдение получает первый слот, остальные выбираются от старых к новым. Текст читается порциями до 768 байт с сохранением целых UTF-8-символов. Подтверждается только фактически включённый диапазон; оставшийся текст продолжает ожидать доставки.
- История: до 32 карточек-кандидатов и восемь сводок до 1536 байт каждая. Полные отчёты автоматически не копируются. Приоритет имеют последний результат, активная работа и замысел, опора и лидер, родитель, связанная неудача, зависимости, недавние результаты и другие направления. Разница с родителем вычисляется только при совпадении метрики, направления, протокола, среды и области оценки и не объявляется причинным эффектом.
- Профиль: компактные сведения о признаках до 10 240 байт, с приоритетом пропусков и новых категорий. Число пропущенных столбцов указано явно; полный профиль и отдельные столбцы доступны через чтение. Цели, ID, небольшие выходные схемы и правила валидации/отбора остаются прямо в защищённом ядре.
- Группы ошибок: не более восьми в запросе, с условиями применимости и ссылкой. Неизвестные ошибки не объединяются по текстовому сходству.
- Поиск: до десяти карточек в пределах бюджета 8192 байта; фильтры по компоненту, движку, статусу, ошибке, протоколу, родителю, среде, инструменту, области и виду записи. Курсор подписан и связан с фильтрами, разрешениями и неизменным срезом журнала. Источники и заметки обнаруживаются через `kind=source` и `kind=research_note`.

Поиск не читает произвольные файлы и не создаёт новые внешние срезы. `allowed_scopes` задаёт контроллер; скрытые контрольные и валидационные метки не входят в поддерживаемые области. Это дополняет проверку доступа у исходного инструмента.

Текст полных контрактов, их цитат, имён столбцов и профилей сохраняет отметку `external_data`. Подтверждённая компактная проекция задачи остаётся состоянием контроллера; произвольный текст внутри исходного документа не приобретает полномочий инструкции. Полные политики публикует только контроллер.

Четыре стадии подгонки: подробности и карточки → карточки со ссылками → сокращённые необязательные сведения и восемь карточек → защищённое ядро и наблюдения. Попытки не перечитывают SQLite, не пересчитывают профиль и не меняют снимок. Невместимость минимального запроса даёт `BudgetExceeded`; основной контроллер должен перейти к предусмотренному завершению с имеющимся результатом.

Размер считается по полному сериализованному запросу: UTF-8-байты плюс резерв выходных токенов. Это консервативная оценка, не подсчёт входных токенов. `B_MIN=131072`, защитный запас — 8192, штатный резерв ответа — 32768. Увеличенный резерв требует увеличения бюджета. Системные инструкции, схемы и обрамление отдельно ограничены 49152 байтами. Фактический отказ API по контексту учитывается отдельно.

Каждый запрос сохраняет точное тело и SHA-256, размеры блоков, все попытки, выбранные ID, версии источников и число чтений. Исключённые ID определяются точным предикатом неизменяемого журнала и выдаются страницами через `excluded_ids(request_id)`. Это позволяет восстановить их полный список без загрузки всей истории при каждой сборке.

## Граница готовности

Офлайн-проверки отдельного модуля завершены. Они включают сбои и перезапуск, атомарность, большой контракт, поиск среди 1000 экспериментов, четыре попытки подгонки и три последовательных сокращения с продолжением сравнения в обоих транспортах. Поведение живого Qwen этим не установлено.

Интеграция выполнена, экономия серверных токенов измерена короткой серией для v016. Длительная сравнительная программа из `ACCEPTANCE_PROTOCOL.json` по текущему поручению не запускалась. Улучшение качества моделей, доля сборки не более 2% времени полной задачи и общая надёжность на неизвестных задачах не установлены. Короткие фактические проверки и ограничения описаны в отчёте v016; отправки этой версии на платформу не было.
