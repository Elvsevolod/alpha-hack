# План приведения AutoML-агента к инструментам с чёткими действиями и проверяемыми результатами

## 1. Цель, исходная база и последовательность работы

Цель — построить понятный и проверяемый цикл:

**Qwen формулирует вопрос → выбирает конкретную операцию → программа выполняет её по заданным правилам → результат попадает в следующий запрос Qwen → модель интерпретирует сведения и выбирает дальнейшее действие.**

Расчёт статистики, обучение, подбор параметров по заданному алгоритму, оценка метрик и контроль ограничений остаются в программе. Qwen отвечает за содержательную интерпретацию, формирование гипотез, изменение стратегии поиска и выбор экспериментов.

План реализуется позже, после завершения текущей разработки. Поэтому исходной базой становится **готовая версия проекта на момент начала работ**, обозначенная **R**. Историческая v011 и ранее найденные дефекты служат материалом для регрессионных проверок.

Работы выполняются в следующем порядке:

1. **Зафиксировать R:** исходники, зависимости, схемы тулов, параметры Qwen, версию механизма контекста и результаты текущих проверок.
2. **Проверить уже написанный механизм контекста** по разделу 4. Исправлять только подтверждённые нарушения; прошедшие проверку компоненты использовать.
3. **Ввести новый интерфейс инструментов** и подключить к нему существующие исполнители.
4. **Исправить и проверить поиск, чтение, историю и повторные обращения.**
5. **Обновить инструкции Qwen, трассировку и сценарии оценки поведения.**
6. **Выполнить адресные офлайн-проверки и небольшую парную проверку пользы нового варианта.** Основная живая программа — 12 прогонов; ещё четыре допускаются только для подтверждения найденного прироста и при выполнении условий бюджета.
7. **Проверить интеграцию и собрать новую поставку**, сохранив прежние версии и результаты.

## 2. Целевой интерфейс инструментов

### 2.1. Реестр действий

Закрепить 14 инструментов как проверяемый вариант интерфейса. Польза обновлённого слоя инструментов проверяется сравнением из раздела 5.4; само число инструментов не считается ни преимуществом, ни дефектом. Работу существующих исполнителей обучения сохранить; новые границы в первую очередь касаются получения сведений и изменения протокола.

| Инструмент | Конкретное действие программы | Результат для Qwen |
|---|---|---|
| `get_dataset_report` | Вычисляет выбранный отчёт по разрешённой области данных | Статистика, область расчёта, ограничения и продолжение выдачи |
| `revise_validation` | Проверяет запрошенный пересмотр; при допуске запускает переоценку сопоставимых кандидатов и может изменить активный протокол в рамках этого же вызова | Решение проверки, состояние пересмотра, прежний и действующий протоколы, результаты переоценки либо причина отказа |
| `search_knowledge` | Выполняет один поисковый запрос заданным способом | Найденные записи, признаки совпадения, ранги, способ поиска и следующая страница |
| `list_knowledge` | Возвращает страницу каталога по фильтрам | Перечень доступных источников, методов, рецептов или пространств параметров |
| `read_knowledge` | Читает конкретный источник или его фрагмент по ID | Содержимое, происхождение, диапазон и продолжение |
| `search_run_records` | Ищет разрешённые записи текущего запуска по структурированным признакам и тексту | Карточки подходящих записей и курсор |
| `list_run_records` | Перечисляет записи запуска по типу и фильтрам | Страница карточек экспериментов, операций, наблюдений или заметок |
| `read_run_records` | Читает выбранные записи, разрешённые разделы контрактов и сохранённый код | Подробности с версией, областью и происхождением |
| `train_model` | Обучает заданный готовый пайплайн | Проверенный результат эксперимента |
| `run_automl` | Запускает ограниченный поиск FLAML или AutoGluon | Результат поиска и выбранной модели |
| `tune_model` | Запускает Optuna для заданной модели и пространства параметров | Проверенные параметры, затраты и результат |
| `run_custom_experiment` | Выполняет переданный Python-компонент: пайплайн, преобразователь или анализ fit | Предсказания либо проверенные агрегаты и диагностика |
| `build_ensemble` | Объединяет совместимые сохранённые предсказания установленным способом | Самостоятельный результат ансамбля |
| `finish` | Необратимо фиксирует завершение исследования | Переход к контролю, выбору победителя и refit |

`analyze_experiments` заменяется инструментами чтения и поиска записей. Содержательное сравнение результатов выполняет Qwen; необходимые вычисления выполняются существующими алгоритмами или явно переданным кодом.

`get_dataset_report` сохраняет известные отчёты: профиль, словарь, пропуски, категории, корреляции и разрешённые срезы. Изменение validation выделяется в отдельную операцию с явными последствиями.

Короткое описание `revise_validation` для Qwen прямо сообщает: это операция с изменением состояния, которая может переоценить кандидатов и применить новый активный протокол. Отдельного последующего подтверждения для применения нет. Метрика, роли, схема выхода и закрытый контроль остаются неизменными.

### 2.2. Контракты вызовов и результатов

Для каждого инструмента определить:

- допустимые аргументы, значения по умолчанию и несовместимые сочетания;
- выполняемый алгоритм и возможные изменения состояния;
- отдельную типизированную модель результата;
- статусы, коды ошибок и условия повторного обращения;
- правила доступа к данным, пагинации и ограничения размера ответа.

Общая часть результата содержит:

- имя инструмента и `operation_id`;
- устойчивый `observation_id`;
- статус и данные по схеме конкретного инструмента;
- происхождение: ID, версия, хеш, область данных и протокол, когда применимо;
- признак полноты;
- маршрут продолжения: имя инструмента и готовые аргументы следующего обращения.

Статусы должны различать отсутствие совпадений, неоднозначность, отсутствующую версию, неизвестный ID, несовместимость, технический отказ и успешное исполнение. Успешный вызов поиска не означает, что найден ответ на исследовательский вопрос.

Для `read_run_records` разрешить пакетное чтение до десяти записей. Чтение кода требует ровно одного объекта. Большой код и текст выдаются страницами.

В результате `revise_validation` отдельно передавать:

- `decision`: допущен или отклонён запрошенный пересмотр;
- `revision_status`: отклонено, переоценка выполняется, изменение зафиксировано, завершено, прервано до фиксации или исход не подтверждён;
- `previous_protocol_hash`, `proposed_protocol_hash` и `active_protocol_hash`;
- ID переоценённых и ожидающих кандидатов, подтверждённые исходы и причину отказа или прерывания.

До атомарной фиксации нового протокола действующим остаётся прежний. Отказ и прерывание до фиксации сохраняют его и прежний пригодный CSV. После фиксации применяется существующая процедура восстановления новой версии и публикации без отката идентичности операций. Неизвестный исход не разрешает слепой повтор обучения. Проверки идемпотентности и восстановления распространяются на новое публичное имя.

Native- и JSON-транспорт используют один реестр схем и одинаковые правила проверки. Версия API инструментов задаётся контроллером и сохраняется в журнале; модель её не выбирает.

### 2.3. Совместимость и восстановление

Новый интерфейс получает `tool_api_version=2`.

- Новые запуски используют отдельное пространство `run_id` с версией API.
- Старые журналы сохраняются без автоматической миграции и продолжаются своим зафиксированным runtime.
- Попытка открыть старый запуск новым несовместимым runtime завершается до обучения с понятной диагностикой.
- Старые имена тулов отсутствуют в публичной схеме API v2.
- Все формируемые контроллером ссылки и параметры продолжения используют новый реестр действий.
- Сохранённые цитаты и исторические записи сохраняют исходное происхождение и названия.

Полные контракты задачи, метрики, границы данных, правила выбора моделей и финализации продолжают проверяться контроллером.

## 3. Поиск, получение сведений и цикл решений

### 3.1. Алгоритмы поиска по базе знаний

`search_knowledge` принимает коллекцию, запрос, фильтры, стратегию, размер страницы и курсор.

Коллекции: документы API и руководства, методы, рецепты, пространства параметров.

Закрепить следующие стратегии:

- **`exact_symbol`:** точное API-имя либо однозначное короткое имя внутри заданных фильтров. При нескольких вариантах возвращается неоднозначность со списком кандидатов.
- **`fts`:** существующий SQLite FTS5 с BM25 для документов.
- **`lexical`:** сопоставление нормализованных слов с индексируемым текстом и символами; учитываются только записи с положительным совпадением.
- **`auto`:** точное разрешение символа, затем FTS5; при отсутствии совпадений или недоступности FTS5 — лексический резерв. Для каталогов используется лексический поиск.

В ответе всегда указывать фактически использованный способ и причину перехода к резервному. Для неподдерживаемой комбинации коллекции и стратегии возвращать явную ошибку.

Дополнительные правила:

- Фильтры применяются **до** ограничения размера выдачи.
- При равных оценках используется устойчивый порядок по ID.
- Лексический балл и BM25 сопровождаются описанием направления оценки; они не представляются вероятностью правильного ответа.
- Поиск возвращает краткие фрагменты и метаданные. Полное содержимое читается через `read_knowledge`.
- `list_knowledge` принимает фильтры без поискового запроса. Его ответ явно обозначается как просмотр каталога.
- Неподдерживаемая версия не заменяется другой версией молча.
- Применимость рецепта и наличие его документации обозначаются раздельно.

Используются существующий корпус, SQLite и разрешённые зависимости.

### 3.2. Пагинация и обнаружение источников

Устранить неоднозначность текущего `cursor`.

- Курсор поиска обозначает продолжение списка результатов.
- Курсор чтения обозначает продолжение содержимого одного источника.
- Курсор содержит версию формата, идентичность запроса, фильтров, источника или снимка и позицию продолжения.
- Изменение запроса, фильтров, стратегии или версии делает прежний курсор недействительным.
- Для поиска возвращаются число совпадений и `next_cursor`; для чтения — фактический диапазон и продолжение.
- Размер страницы — до десяти карточек, с дополнительным ограничением бюджета наблюдения.
- Следующая страница продолжается после фактически выданных элементов, включая случаи уменьшения страницы из-за размера ответа.

Для источников использовать ссылку с коллекцией, ID и версией корпуса: одинаковые имена в разных каталогах не должны смешиваться.

При фрагментировании документов сохранять границы разделов и блоков кода, когда они помещаются в бюджет. Для большого блока явно обозначать частичный фрагмент и продолжение. Сигнатура API должна сохранять связь с условиями и предупреждениями.

### 3.3. Повторный поиск и остановка

В инструкциях Qwen закрепить такой порядок:

1. Сформулировать, каких сведений не хватает.
2. Выполнить конкретный запрос.
3. Оценить полученные кандидаты и прочитать нужные фрагменты.
4. При недостаточности сведений изменить запрос, фильтры, стратегию, страницу или обратиться к каталогу.
5. После получения свидетельств сформулировать гипотезу и выбрать действие.
6. Если сведения получить не удалось — зафиксировать конкретный пробел и выбрать допустимую альтернативу либо завершение.

Последовательность вызовов выбирает Qwen. Программа обеспечивает доступные действия, проверку ограничений и наблюдаемость.

В журнале сохранять запрос, фильтры, способ поиска, просмотренные страницы, найденные ID и фактически переданные фрагменты.

При оценке прогресса:

- новый текст запроса сам по себе не считается новым свидетельством;
- повторная выдача уже полученных сведений не сбрасывает стагнацию;
- пустая выдача относится к конкретному запросу и версии корпуса;
- неудача поиска не считается неудачей модели или семейства ML-алгоритмов;
- общий дедлайн, резерв завершения и действующие правила бесполезных обращений сохраняются.

### 3.4. Поиск по истории и связь с экспериментами

`search_run_records` использует структурированные фильтры: компонент, движок, статус, код ошибки, протокол и родитель. Текстовый запрос выполняется по разрешённым диагностическим полям и гипотезам через нормализацию регистра и буквальное сопоставление слов. Пустой запрос без фильтров перенаправляется диагностикой к `list_run_records`.

История индексируется и читается через разрешённые представления записей. Поиск не предоставляет доступа к скрытым меткам, произвольным файлам или новым внешним срезам.

Для гипотез добавить необязательные `evidence_refs` — ссылки на наблюдения, источники и результаты. Контроллер проверяет существование, доступность и идентичность ссылок.

В трассировке различать:

- источник найден;
- содержимое включено в запрос модели;
- получена допустимая команда после передачи содержимого;
- с источником связан выполненный эксперимент.

Одна ссылка в гипотезе не подтверждает применение источника. Для этого проверяются переданный фрагмент, фактическое изменение конфигурации или кода и исполненный результат. Причинную пользу справки оценивают отдельным сравнением.

## 4. Проверка уже написанного управления контекстом

На старте работ выполнить проверку готового механизма. Для каждого пункта оформить результат: **подтверждено**, **обнаружен дефект**, **не хватает проверки**. Реализацию, прошедшую проверку, подключить к новому API без повторного проектирования.

### 4.1. Надёжность доставки наблюдений

Проверить полный путь от завершения тула до следующего решения:

- результат операции и ожидающее доставки наблюдение сохраняются атомарно;
- включение в запрос фиксируется по хешу фактического сериализованного запроса;
- передаётся само содержимое запрошенного фрагмента;
- ошибка API, тайм-аут, обрезанный ответ или недопустимая команда сохраняют наблюдение ожидающим;
- ошибка канала хранится отдельно от результата инструмента;
- подтверждение доставки связывается с устойчиво зарегистрированной допустимой командой;
- перезапуск восстанавливает очередь и команду без повторного исполнения завершённой операции.

Повторить прежний сценарий с 2500 символами документации: при достаточном бюджете текст должен присутствовать в следующем запросе при любом уровне сжатия. При уменьшении порции должны присутствовать содержимое выданной части и рабочее продолжение.

Отдельно проверить чтение кода после ошибки, повторное чтение, переключение транспорта и сбой между регистрацией команды и её исполнением.

### 4.2. Состояние исследования и ограниченность памяти

Проверить сохранность:

- активного вопроса и `research_note`;
- опоры, лидера и родителя сравнения;
- связанной неудачи и необходимых зависимостей;
- версии протокола и области результатов;
- очереди недоставленных наблюдений;
- исходного дедлайна и счётчиков.

Предположения Qwen должны оставаться помеченными как предположения.

Группировка ошибок должна учитывать компонент, движок, операцию, среду и протокол. Неизвестные ошибки нельзя объединять только по похожему тексту. Технический отказ, неизвестный исход и завершённое ухудшение метрики должны оставаться различимыми.

Обязательная проверка истории: среди 1000 различных результатов найти старую неудачу по структурированным признакам, без известного ID, и прочитать нужную диагностику не более чем за три обращения. Проверить обнаружение старых заметок и чтение полных разделов контрактов.

### 4.3. Бюджет и стоимость сборки запроса

Сохранить требования согласованного контекстного плана:

- компактное ядро — не более 16 КиБ;
- предусмотренное минимальное наблюдение — 8 КиБ;
- минимальный поддерживаемый бюджет — 131072 единицы действующей консервативной оценки;
- полный запрос проверяется с инструкциями, схемами, обрамлением и резервом ответа;
- оценка по байтам не называется точным числом токенов.

После перехода к 14 тулам заново измерить оба транспорта. Проверить предел 49 КиБ для инструкций, схем и обрамления, установленный контекстным планом.

На одно решение должен создаваться один согласованный снимок. До четырёх попыток подгонки работают с этим снимком, не перечитывая всю историю и не пересчитывая профиль.

При недостаточном бюджете сохраняются наблюдение и история, фиксируется причина и выполняется предусмотренное завершение. Локальная подгонка запроса не считается ошибкой API или неудачным исследованием.

Проверить установленные показатели производительности:

- история из 100, 1000 и 10000 записей; оба транспорта; по 30 измерений после прогрева;
- p95 сборки со всеми попытками ≤ 0,5 с, максимум ≤ 2 с;
- дополнительная пиковая память ≤ 64 МиБ;
- тёплая сборка за весь прогон ≤ 2% общего времени;
- холодный профиль 256 строк × 10000 признаков ≤ 30 с, без повторного расчёта при подгонке.

### 4.4. Интеграция с новыми инструментами

Проверить все маршруты чтения, которые формирует механизм контекста. Они должны строиться через реестр API v2.

Найденные источники, выданные фрагменты и подтверждённая доставка учитываются раздельно. Удаление подробностей из входа модели сохраняет возможность обнаружить и прочитать их повторно.

Полные контракты и проверки остаются у контроллера. Справка, код и результаты программ сохраняют происхождение и границы доверия после сжатия и восстановления.

## 5. Приёмка, ограничения расхода и поставка

### 5.1. Офлайн-приёмка

Во время разработки запускать адресные проверки изменённых контрактов, маршрутов и прежних дефектов. После сборки кандидата один раз выполнить действующий набор технических тестов. Повторять полный набор при новых изменениях или обнаруженных регрессиях; подходящие проверки раздела 4 использовать повторно как свидетельства, без дублирующих запусков.

| Область | Обязательные сценарии |
|---|---|
| Контракты | Все 14 действий, ошибочные аргументы, неизвестные ID, несовместимые режимы, одинаковое поведение транспортов |
| Пересмотр validation | Отказ без изменения протокола, допуск и переоценка, атомарная фиксация, прерывание до и после фиксации, повтор операции и восстановление |
| Поиск | Точный символ, неоднозначность, отсутствующая версия, пустая выдача, недоступный FTS5, лексический резерв |
| Фильтрация | Фильтры применяются до ограничения выдачи; подходящие документы не теряются из-за общего лимита |
| Пагинация | Разные страницы, завершение выдачи, перезапуск, изменённый запрос, устаревший курсор, UTF-8 и большие фрагменты |
| Каталоги | Просмотр каталога отделён от совпадения с запросом; нулевые совпадения не маскируются |
| История | Старые результаты и ошибки находятся без ID; протоколы и области сохраняются; код доступен по корректной ссылке |
| Наблюдения | Реальное содержимое следующего запроса, сбои канала, недопустимая команда, перезапуск и повторная доставка |
| Прогресс | Перестановка результатов, новый ID или косметическая переформулировка не создают ложного прогресса |
| Обучение | Все существующие движки и семейства задач, собственный анализ, ансамбли, контроль, refit и сохранение CSV |
| Границы доступа | Поиск и чтение не расширяют доступ к данным; внешние инструкции не меняют политики контроллера |
| Транспорт | Выбранная на R политика одного вызова за решение, разбор неправильного ответа, переход транспорта и сохранность ожидающего наблюдения |

Сохранить успешные пары запрос–документ на зафиксированном базовом поисковом наборе. Результаты сверять по одинаковым данным и версии корпуса.

Каждый дефект из прежнего аудита должен получить регрессионную проверку, даже если он уже устранён текущей разработкой.

### 5.2. Отдельная проверка релевантности поиска

Прежний регрессионный набор и новый итоговый набор оцениваются раздельно. Сохранение прежних попаданий проверяет совместимость, а новые запросы — поведение поиска на других формулировках и близких неподходящих источниках.

До настройки ранжирования и итогового запуска зафиксировать 24 новых запроса на существующем корпусе:

| Группа | Число | Что проверяется |
|---|---:|---|
| Переформулировки | 4 | Другие русские и английские формулировки вопросов, для которых есть подходящий источник |
| Смешанный язык | 4 | Русский вопрос с английскими терминами, API-именами и сокращениями |
| Близкие неподходящие документы | 4 | Похожие имена, другая библиотека, задача, операция или условия применимости |
| Сочетания условий | 4 | Несколько требований, фильтры и версии при наличии подходящего документа |
| Отсутствующий материал | 4 | Два отсутствующих точных объекта и два содержательных вопроса с похожими источниками, но без требуемого ответа |
| Отсутствующая версия | 4 | Известный API или документ с недоступной в корпусе явно указанной версией |

Для каждого запроса заранее сохранить стратегию, фильтры, допустимые ID, версии, основание релевантности и ID близких неподходящих документов. Для отрицательных случаев сохранить ожидаемый тип реакции. Четыре запроса из положительной части пометить как критичные обращения к API; для них дополнительно перечислить необходимые сигнатуры, условия и предупреждения.

Итоговый набор не используется для изменения алиасов, весов, правил ранжирования или порогов. Настройка выполняется на отдельном разработческом наборе. После просмотра итоговых результатов изменение поисковых правил требует нового зафиксированного итогового набора и версии протокола.

Пороги приёмки:

- Подходящий источник найден в первых пяти результатах не менее чем для 14 из 16 положительных запросов; в каждой положительной группе — не менее 3 из 4.
- MRR@5 — среднее обратной позиции первого подходящего результата, с нулём при отсутствии в первых пяти — не ниже 0,75 на 16 положительных запросах.
- Для всех четырёх критичных API-запросов нужный источник входит в первые пять, версия соблюдена, а прочитанные фрагменты сохраняют необходимые условия и предупреждения. Частичный фрагмент сопровождается продолжением и не обозначается полным.
- Для двух отсутствующих точных объектов и четырёх отсутствующих версий требуемая отрицательная реакция получена во всех случаях; подмена объекта или версии недопустима.
- Для двух содержательных вопросов без ответа лексические кандидаты не обозначаются подтверждённым ответом. Отдельно публикуются нерелевантные кандидаты и их позиции. Это не считается доказательством способности алгоритма установить семантическое отсутствие ответа; решение Qwen при нехватке сведений проверяется сценарием S4.

Оценивать FTS5 и лексический резерв отдельно, когда они поддерживаются соответствующей коллекцией; итоговые пороги относятся к основной стратегии auto. Публиковать состав выдачи, Hit@5, MRR@5, реакции на отсутствие материала и версии и проверку читаемых фрагментов. Все проверки этого раздела выполняются офлайн, без новой поисковой модели и обращений к Qwen.

### 5.3. Короткая живая проверка поведения Qwen

Выполнить **четыре сценария по одному разу**, без отдельной серии повторов каждой ветви. Полноту контрактов и обоих транспортов проверять офлайн; живые сценарии подтверждают, что Qwen использует результаты для следующего решения.

| ID | Поведение | Критерий успеха | Транспорт |
|---|---|---|---|
| S1 | Неудачный или неоднозначный поиск, уточнение и чтение | Qwen получает подходящий источник нужной версии и использует его в выполненном эксперименте | native |
| S2 | Поиск старой ошибки и восстановление после устаревшего ID, курсора или неверного аргумента | Qwen использует диагностику, обнаруживает нужную запись и выполняет исправленный допустимый вызов | JSON |
| S3 | Отказ в пересмотре validation и использование отчёта о данных | Протокол и закрытый контроль сохранены; Qwen выбирает допустимый эксперимент с учётом конкретного свойства данных | native |
| S4 | Нехватка сведений или ресурсов и завершение | Qwen фиксирует причину и выбирает допустимую альтернативу или finish; пригодный обученный CSV и предусмотренная финализация сохранены | JSON |

Для каждого сценария до запуска выбрать конкретную ветвь, исходное состояние и предикаты успеха. В S2 допустима заранее объявленная инъекция отказа; следующее решение принимает настоящий Qwen. В S3 сохраняются причина отказа и хеши протокола до следующего решения. Если S4 проверяет нехватку ресурсов, оставить бюджет одного решения Qwen и финализации: завершение самим контроллером до ответа модели не подтверждает выбор finish моделью.

Пределы одного сценария: 180 с, 1 CPU, 2 ГиБ RAM, seed обучения 42, не более восьми фактических запросов к Qwen и трёх исследовательских кандидатов сверх подготовки. Все повторы API и переходы транспорта входят в лимит. Проверять фактический транспорт; JSON после резервного перехода не подтверждает native.

Сохранять наблюдаемое использование результата, выполненные команды и исходы всех четырёх попыток. Для прохождения нужны все четыре случая и ноль нарушений инвариантов. Готовые живые свидетельства могут закрыть сценарий при совпадении хеша поставки, API, настроек и условий. При провале обязательного сценария сначала устранить дефект; к парному сравнению такого кандидата не переходить. Неуспешный случай не заменяется дополнительной удачной попыткой. Эти сценарии проверяют работоспособность; прирост оценивается разделом 5.4.

### 5.4. Малое парное сравнение пользы нового варианта

**Главная цель — показать улучшение качества итоговой модели при одинаковом бюджете.** Прирост оценивается по внешним RMSE и Macro F1. Число обращений, ошибки и расход помогают объяснить результат; сами по себе они не подтверждают рост ML-качества.

После проверки R зафиксировать общую основу C: R с обязательными исправлениями доставки, безопасности и общих исполнителей, если они понадобились. Если R уже выполняет эти требования, C совпадает с R. От C построить:

- **I_old:** прежний слой инструментов, схемы и соответствующие инструкции Qwen;
- **I_v2:** новый реестр из 14 инструментов и предусмотренные разделами 2–3 изменения поиска, чтения и истории.

Одинаковыми остаются механизм контекста и его параметры, ML-исполнители, корпус, данные, разбиения, оценщик, ограничения доступа и финализация. Различия слоя инструментов и необходимые адаптации ссылок фиксируются в манифесте. Сравнение показывает эффект всего обновления инструментов; вклад одного переименования отдельно не исследуется. Улучшения моделей, дополнительные источники и посторонние изменения только в один вариант не добавляются.

До запуска зафиксировать четыре небольшие итоговые задачи, которые не использовались для настройки нового варианта:

| Задача | Содержание | Транспорт |
|---|---|---|
| T1 | Регрессия с пропусками и категориями | native |
| T2 | Регрессия с временной или групповой структурой | JSON |
| T3 | Классификация с редкими классами и новыми категориями | native |
| T4 | Классификация с текстовыми признаками | JSON |

Задачи должны позволять обучить опору, выполнить исследование и обязательную финализацию за выбранный срок; это проверяется офлайн. Метки итогового test доступны только внешнему оценщику. Итоговые задачи, разметку и пороги не подбирать по уже полученным результатам I_v2.

**Основная серия: четыре задачи × одна пара × два варианта = восемь прогонов.** Seed обучения — 42. В каждой паре одинаковы модель Qwen, параметры генерации, транспорт и пределы: 300 с, 4 CPU, 10 ГБ RAM, до 12 фактических запросов к Qwen, включая повторы и переход транспорта. Оба варианта стартуют из отдельных чистых каталогов на одном хосте. Порядок I_old/I_v2 чередуется между задачами и фиксируется заранее. Отдельно от seed обучения сохранять версию Qwen, параметры генерации, поддерживаемый seed модели и fingerprint, если они доступны.

До запуска зафиксировать правила оценки:

| Показатель | Правило |
|---|---|
| Инварианты и завершение | Ноль нарушений контрактов, доступа, доставки и идемпотентности; у I_v2 валидный обученный CSV и предусмотренные control/refit во всех парах |
| Практический прирост RMSE | Снижение RMSE не менее чем на 2% относительно I_old; относительная разница считается с нижней границей знаменателя 1e-12 |
| Практический прирост Macro F1 | Увеличение Macro F1 не менее чем на 0,01 в единицах метрики |
| Допустимое ухудшение отдельной пары | Рост RMSE не более 1% либо снижение Macro F1 не более 0,005 |
| Положительный сигнал основной серии | Практический прирост не менее чем на двух из четырёх задач, остальные пары укладываются в допуск ухудшения |

Сначала проверить полноту серии: для сравнения качества нужны пригодные CSV обоих вариантов во всех четырёх парах. При нехватке результатов статус — **«сравнение не завершено»**, причина и все попытки сохраняются. Если полная основная серия не показывает положительный сигнал, зафиксировать **«прирост не показан»** и остановить живое сравнение. Ошибки и трассы использовать для доработки на разработческом наборе. Порог и итоговый набор не менять ради удачного исхода; дополнительные попытки не присоединять к серии для замены неудач.

**Подтверждение найденного эффекта: ещё две пары — четыре прогона.** Заранее назначенные задачи T1 и T4 повторяются с seed обучения 17 при прежних условиях. Их выбор фиксируется до основной серии, без отбора наиболее удачных задач. Код кандидата между основной и подтверждающей частями не меняется. Для подтверждения нужен практический прирост хотя бы в одной из двух дополнительных пар и соблюдение допуска ухудшения в другой. Все результаты основной серии остаются в отчёте. Если эффект не повторился, статус — **«первичный прирост не подтверждён»**. Максимум сравнения — 12 прогонов; вместе с разделом 5.3 — максимум 16.

Для каждого прогона публиковать итоговую метрику, изменение относительно пары, результат завершения, число фактических обращений и ошибочных вызовов, полное время и серверный расход токенов. В затраты входят подготовка, поиск, чтения, ошибки, повторы, смена транспорта и финализация. При отсутствии достаточного usage расход токенов помечается неизвестным; рост ML-качества оценивается по внешней метрике. Соблюдение строгого бюджета проверяется отдельно по разделу 5.5.

Корректное завершение с уже обученной опорной моделью оценивается по итоговому CSV, качеству и затратам на общих основаниях. Количество запросов до первого исследовательского эксперимента — дополнительная диагностика для пар, где он был у обоих вариантов. Для остальных сохранять отсутствие события и причину завершения; этот показатель не блокирует приёмку и не подменяется нулём.

Неуспешные и неполные прогоны сохраняются. При отсутствии сравнимого CSV или подтверждающих пар прирост остаётся неподтверждённым. Малый набор даёт начальное измерение и проверку повторяемости эффекта на выбранных задачах, а не статистическую гарантию преимущества на всех неизвестных данных. Следующая версия кандидата оценивается по новому зафиксированному протоколу; увеличение числа прогонов до получения успеха не предусмотрено.

### 5.5. Строгий предел расхода API

Уже при фиксации R проверить техническую возможность гарантировать предел. Для всей дополнительной живой приёмки API v2 установить один общий бюджет:

**B = 10% подтверждённого доступного остатка перед началом дополнительной живой приёмки.**

Основная программа — **четыре коротких сценария и восемь прогонов сравнения (четыре пары), всего 12**. При положительном сигнале допускаются ещё четыре подтверждающих прогона, поэтому **абсолютный предел — 16 живых прогонов**. Пилоты с Qwen и диагностические обращения выполняются внутри этих прогонов и их лимитов; повторы API и переходы транспорта также входят в общий B. Самостоятельная предварительная живая серия не добавляется. Начало очередной подсерии не создаёт новый бюджет в 10%.

Начинать живые вызовы разрешается только при одном из двух условий, в указанном порядке:

1. Организаторский API обеспечивает жёсткий подлимит для всей дополнительной приёмки, не превышающий B.
2. Имеется подтверждённая верхняя стоимость каждого запроса в единицах бюджета; перед вызовом резервируется её максимум, включая возможные повторы, и сумма расходов и оставшихся резервов не превышает B.

Проверки `/key/info`, ограничения времени, числа запросов и токенов используются дополнительно. Они не заменяют гарантию потолка расхода.

Если ни одно условие не выполнено, офлайн-работа продолжается, а живая приёмка получает статус **«не выполнена: строгий предел расхода не обеспечен»**. Перед основной серией проверить возможность зарезервировать расход с учётом предусмотренного подтверждения. При нехватке бюджета завершённые результаты сохраняются, а недостающие проверки остаются неподтверждёнными. Бюджет и предел числа прогонов не расширяются автоматически; пороги прироста не ослабляются.

Для каждой подсерии обязательны отдельные снимки before и after по правилам `alpha-api-limits`; общий журнал учитывает совокупный бюджет. Неизвестный остаток или непроверяемый расход не выдаются за соблюдение бюджета. Изменение общего счётчика при других запусках на том же ключе не приписывается автоматически этим прогонам.

### 5.6. Согласование с контекстной и общей приёмкой

- Сравнение B0/B1/N и расширенные контекстные сценарии относятся к отдельному плану. Его 120 сравнительных и 15 сценарных прогонов не добавляются к приёмке инструментов и не становятся условием подтверждения прироста этого этапа.
- При сравнении вариантов с API v2 новый интерфейс инструментов должен быть одинаковым во всех трёх вариантах. Эффект смены интерфейса не смешивается с эффектом сжатия.
- I_old/I_v2 проверяет весь обновлённый слой инструментов при одном механизме контекста; B0/B1/N проверяет механизм контекста при одном интерфейсе. Выводы о пользе инструментов и сжатия формулируются раздельно.
- Результаты старых исходников сохраняются с прежними хешами и не подтверждают автоматически новую поставку.
- Доставку и восстановление при длительном давлении на контекст проверять офлайн на интегрированном runtime; подходящие свидетельства раздела 4 использовать без повторной серии.
- Основная приёмка проекта проводится в согласованном профиле: сейчас 6 CPU и 5 ГиБ на задачу, с параллельной трёхчасовой репетицией двух задач. Эта репетиция относится к выпуску всего проекта и не повторяется отдельно для каждой проверки инструментов.
- При изменении профиля до начала реализации фиксируется новый протокол и повторяются затронутые проверки.

Техническая готовность требует ясных контрактов, обязательных офлайн-проверок, проверки поиска, подтверждённой доставки и четырёх живых сценариев. Для принятия нового варианта с заявленным приростом дополнительно нужны положительный сигнал основной серии и его подтверждение по разделу 5.4. Технически исправный вариант без этого результата получает статус **«работает, прирост не подтверждён»** и не объявляется улучшением. Общая цель качества по RMSE и Macro F1 сохраняется как отдельный критерий проекта.

### 5.7. Результаты и выпуск

Подготовить:

- реестр API v2 с аргументами, результатами, ошибками и последствиями действий;
- обновлённую схему маршрутов вызовов;
- матрицу соответствия требованиям и результатам проверок;
- результаты четырёх коротких живых сценариев с фактическим транспортом;
- трассы запросов, вызовов, доставки наблюдений и повторного поиска;
- отчёт о проверке готового механизма контекста;
- отчёты офлайн- и живой приёмки с исходами всех попыток;
- отдельные результаты по прежнему поисковому набору и 24 новым запросам с разметкой релевантности;
- манифест I_old/I_v2, состав общих исправлений C, все восемь основных и до четырёх подтверждающих исходов, парные изменения ML-метрик и решение о наличии прироста;
- сводный журнал единого бюджета дополнительной живой приёмки;
- новую нумерованную поставку через существующий упаковщик.

Сохранить штатный запуск, исходные зависимости и плоский формат архива. Старые архивы, журналы и замороженные сравнительные серии сохранить.

Кандидат и его техническая приёмка оформляются отдельно от полной готовности проекта. Указатель принятой версии обновляется после выполнения всех относящихся к ней критериев; автоматическая отправка на платформу в этот план не входит.
