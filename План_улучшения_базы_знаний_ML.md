# Официальная офлайн-база знаний для ML-агента

Редакция с учётом аудита. Этот документ описывает будущую реализацию; измерения, сборка нового корпуса и приёмочные прогоны по нему ещё не выполнены.

## 1. Цель и принцип работы

Собрать подробную официальную документацию выбранных ML-библиотек **именно тех версий, которые указаны в `data_for_participants/requirements.txt`**, и улучшить поиск, передачу материалов и память агента.

Документация собирается **заранее, при подготовке решения**: из официальных источников и документационных строк установленных пакетов точных версий. Затем тексты и индекс встраиваются в `agent_bundle.py`. В контейнере организаторов решение восстанавливает локальную базу и читает её без интернета. Разрешённый канал Qwen работает отдельно от доступа к сайтам документации.

Сохранить наши исходные решения: полный доступный официальный корпус выбранных библиотек, точные версии, автоматический подбор материалов вместе с самостоятельным поиском, небольшие порции контекста и память содержательных ограничений. Официальную документацию, проектные рекомендации и экспериментальные результаты учитывать раздельно.

Изменения ограничиваются базой знаний и её интеграцией. Новые обучающие адаптеры, изменение протокола оценки и отправка решения на платформу в эту работу не входят. Проверка модуля должна устанавливать наблюдаемое правильное применение или обоснованное отклонение знаний. Выигрыш итоговых ML-метрик требует отдельного исследования.

## 2. Состав, достоверность и воспроизводимость корпуса

- Включить 16 библиотек: scikit-learn, CatBoost, LightGBM, XGBoost, imbalanced-learn, category-encoders, Feature-engine, statsmodels, Optuna, PyTorch, AutoGluon Tabular, LightAutoML, FLAML, NumPy, pandas и SciPy.
- Исключить документацию служебных и LLM-библиотек. Исходный `requirements.txt` сохранить без изменений.
- Для выбранных библиотек собрать полный доступный официальный Python API, руководства, примеры и примечания к соответствующему релизу. Для AutoGluon ограничиться Tabular, для FLAML — AutoML.
- Сохранять полный текст, сигнатуры, таблицы параметров, код, предупреждения и ограничения. Удалять навигацию, оформление сайта, повторяющиеся элементы и двоичные ресурсы. Размер корпуса не ограничивать произвольным количеством первых символов.
- Сделать манифест источников единственным списком библиотек, версий и маршрутов сбора. Версии сверять с `requirements.txt`, устранив дублирующий список внутри сборщика.
- Для каждого источника фиксировать официальный адрес, релиз, подтверждение соответствия версии, commit для репозитория, исходный и нормализованный хеши, лицензию. Для PyTorch использовать релиз `v2.5.1`, для LightAutoML — официальный [релиз `v.0.4.2`](https://github.com/sb-ai-lab/LightAutoML/releases/tag/v.0.4.2).
- Страницу семейства версий, например `1.8.x`, принимать как точную документацию только после подтверждения соответствия нужному patch-релизу. При отсутствии подтверждения использовать официальный снимок точного тега и документацию установленного пакета. Подмену на `latest` исключить.
- Разрешать ссылки, включения и автоматически формируемые разделы документации. Неразрешённые элементы и отсутствующие материалы отражать в отчёте полноты; такой корпус не объявлять полным.
- Переработать все 32 методические карточки: добавить условия применения, противопоказания, стоимость, минимальный эксперимент и ссылки на подтверждающие разделы. Разделять документированные свойства API и проверяемые проектные гипотезы.
- Удалённую ссылку на `psutil` в карточке бюджетирования заменить ссылкой на собственный контракт ресурсов агента.

**Конечный перечень разделов и полнота**

- До массового сбора сформировать перечень ожидаемых страниц, объектов API и разделов для каждой библиотеки из официальных оглавлений, каталогов API и документов закреплённого релиза. Зафиксировать его хеш.
- Каждому элементу присвоить один из статусов: `included`, `out_of_scope`, `unavailable`, `error`. Для исключения записывать причину и правило области работ; отсутствие источника или нехватка места не считаются исключением по области работ.
- В отчёте показывать абсолютные количества и доли по каждой библиотеке, а также неразрешённые включения. Заявление о полном корпусе допустимо только после включения всех предусмотренных областью работ разделов; `unavailable` и `error` не скрывать из знаменателя.

**Воспроизводимость**

- Зафиксировать единый набор исходных материалов, их хеши, точные версии пакетов, среду сборки с версиями Python и SQLite, версии сборщика, нормализации, разбиения на фрагменты и формата индекса.
- Выполнить две офлайн-сборки в двух разных чистых каталогах из одного зафиксированного набора исходников. Не использовать прежний выходной каталог, промежуточные индексы и неучтённые кэши; сеть отключить.
- Проверить совпадение нормализованных документов, фрагментов, каталогов, индекса и lock-файла. Устранить зависимость от абсолютных путей, порядка обхода, текущего времени и состояния рабочего каталога. Даты получения брать из зафиксированных исходных материалов.
- Воспроизводимость, полноту и правильность версий проверять отдельно: одинаковые хеши неполного корпуса не означают полноту.
- Собирать корпус во временный каталог и заменять рабочий только после проверки. Сохранять предыдущий корпус и его lock-файл для сравнения и восстановления.

## 3. Проверка ресурсной реализуемости до массового сбора

Сначала провести пилот на материалах всех 16 библиотек, включив крупные страницы и длинные руководства PyTorch, pandas, SciPy и AutoGluon. По перечню разделов оценить объём полного корпуса и индекса с запасом, затем измерить реальную сборку, упаковку, восстановление и поиск. Полный корпус после расширения проверить повторно.

Начальные проектные бюджеты приведены ниже. Их достижимость пока не подтверждена; пилот должен проверить её до массового сбора. Все показатели измерять в Linux-среде с точными зависимостями организаторов; для поиска выделить один CPU.

| Показатель | Предельное значение |
|---|---|
| Готовый ZIP решения | 100 000 000 байт |
| Распакованный корпус вместе с индексами | 1 ГиБ |
| Пиковая память восстановления и открытия базы | 1 ГиБ |
| Прирост постоянной памяти из-за открытой базы | 256 МиБ относительно того же агента без расширенной базы |
| Холодное восстановление и первый поиск | 30 секунд, включая импорт встроенного пакета |
| p95 поиска с FTS5 | 0,5 секунды |
| p95 резервного лексического поиска без FTS5 | 2 секунды |

- Холодный запуск измерять без готового каталога `.agent_runtime`; тёплый запуск учитывать отдельно. Для задержек использовать не менее 100 запросов из разработочного набора, измеряя p50, p95, память и объём диска.
- Проверить рост затрат при увеличении корпуса. Пилотная оценка не заменяет измерения полного корпуса и реальной плоской поставки.
- Предусмотреть порционное декодирование и восстановление, ленивое чтение текстов и каталога, устранение дубликатов. Не загружать весь корпус в контекст или память и не удерживать одновременно лишние полные копии встроенного архива.
- Время подготовки базы и поиска учитывать в общем дедлайне задания; резерв обучения, контроля и refit сохранять.
- Если бюджеты не выполняются, сначала изменить хранение и восстановление. Молчаливое сокращение корпуса, исключение библиотек и увеличение бюджетов запрещены; неустранимое превышение требует явного пересмотра плана и отчёта о причине.

## 4. Поиск, интерфейс и окончательный контекст агента

**Поиск и автоматический подбор**

- Индексировать весь корпус по разделам, сохраняя связь фрагмента с исходным документом. Код, таблицы и предупреждения должны оставаться читаемыми и связанными с соответствующим API.
- Объединить поиск по документации, методам, рецептам и пространствам параметров. Указывать тип каждого результата. Применять фильтры библиотеки и версии до ограничения количества результатов.
- При ранжировании учитывать точные символы API, заголовки, русские и английские термины. Сохранить SQLite FTS5 и резервный лексический поиск без новых зависимостей и внешних моделей.
- Перед исследовательским решением формировать активный блок знаний максимум из трёх материалов общим объёмом до 6000 символов, включая выбранные выдержки из памяти и метаданные. Подбирать его по подтверждённой постановке, профилю обучающей части, валидации, текущему пайплайну, ресурсам и последней технической ошибке. Контрольные и скрытые метки в подборе не участвуют.
- Показывать причину выбора, условия применения, существенные ограничения, официальный фрагмент и доступный рецепт. Самостоятельный поиск агента сохранить. Документация PyTorch или LightAutoML не включает отключённый адаптер и не подтверждает исполнение.
- Пересчитывать подбор и применимость при изменении существенного контекста. Повторная передача тех же сведений не считается новым прогрессом.
- Существенное предупреждение и относящееся к нему условие включать вместе с рекомендацией. Если обязательные сведения не помещаются, помечать пакет как недостаточный и указывать требуемое дочитывание; не выдавать сокращённую рекомендацию за готовое основание для действия.
- На испытаниях проверять достаточность по заранее размеченным обязательным сведениям после всех стадий: ранжирования, выбора трёх материалов, сериализации, сокращения контекста и сборки фактического запроса Qwen. При работе агента проверять сохранность известных обязательных условий и предупреждений; полнота ответа на новый произвольный вопрос без эталона этим не подтверждается. Сохранять точный состав переданного блока, его хеш и объём. Проверка промежуточного результата `get_reference` этого не заменяет.

**Контракт `get_reference` и продолжения**

- Сохранить имя инструмента, существующие режимы и ID документов и карточек. В ответах передавать источник, точную версию, ID и хеш документа и фрагмента, условия применимости и статус полноты выдачи. Внутренний поисковый текст не передавать.
- `max_chars` ограничивает полный JSON-ответ, включая метаданные, предупреждения и продолжение. Единица измерения — символы результата канонической сериализации Unicode; транспортные байты и токены учитывать отдельно.
- Вместо непроверяемого положительного смещения использовать непрозрачный токен продолжения в `next_cursor`. Токен связывать с версией корпуса и ранжирования, режимом, запросом, фильтрами, документом и его хешем при чтении, а также позицией продолжения. Если выдача зависит от задачи, валидации или реестра возможностей, включать хеш этого контекста применимости.
- Первый запрос принимает отсутствующий курсор или прежнее значение `0`; положительные числовые курсоры после миграции возвращают `invalid_cursor`. Обновить схему `ReferenceArgs`, внутренние вызовы и тесты. Продолжение передаётся в `cursor` при повторе исходных параметров; `limit` и `max_chars` разрешено менять.
- Изменение запроса, режима, документа или фильтров при использовании токена возвращает `invalid_cursor`; смена корпуса, версии ранжирования или зависимого контекста применимости возвращает `stale_cursor`. Не продолжать чтение молча из другого состояния.
- Различать `not_found`, `missing_version`, `ambiguous_symbol`, `budget_too_small`, `partial`, `invalid_cursor` и `stale_cursor`. Ошибки целостности сохраняют отдельный статус. Отсутствие документа не означает отсутствие API в библиотеке.
- При недостаточном бюджете возвращать минимальный ответ с `status` и `min_chars`, без ложного `not_found`. Если передана только часть материала, указывать причину, продолжение и `answer_usable=false`, когда не вошли известное обязательное условие или предупреждение. Не разрывать предупреждение так, чтобы оставшаяся часть выглядела самостоятельным разрешением.
- При работе агента `answer_usable=true` означает только сохранность известных обязательных условий и предупреждений выбранных материалов. Флаг не доказывает полноту ответа на произвольный вопрос, достаточность источников или применимость рекомендации. Для невычислимой применимости сохранять `unknown` независимо от значения флага; в испытаниях отдельно вычислять достаточность по эталонной разметке.

Примеры поведения, которые закрепляются в тестах:

| Вход или событие | Ожидаемый результат |
|---|---|
| `mode=search`, `query=fit`, `library=catboost`, `version=1.2.8` | Найденные материалы CatBoost 1.2.8; фильтрация выполнена до ограничения выдачи |
| Тот же запрос с `version=999.0` | `missing_version`, без материалов другой версии |
| Посторонний запрос без совпадений, включая режим методов | `not_found`, без случайных карточек |
| Чтение существующего документа с `max_chars=100`, когда обязательные метаданные не помещаются | `budget_too_small` и необходимый минимум; документ не объявляется отсутствующим |
| Чтение с корректным токеном и прежними параметрами | Продолжение того же документа без пропусков и непредусмотренных повторов |
| Тот же токен после смены запроса или фильтра | `invalid_cursor` |
| Тот же токен после смены корпуса | `stale_cursor` |
| Ответ без известного обязательного предупреждения из-за сокращения | `partial`, `answer_usable=false`; в автоматическом пакете такой ответ не считается достаточным |
| Новый вопрос: известные условия сохранены, но применимость невычислима | Допустим `answer_usable=true` вместе с `applicability=unknown`; полнота ответа этим не подтверждается |

## 5. Контракт памяти и жизненный цикл знаний

Хранить полную историю в журнале, а в активный блок выбирать только необходимые сведения с учётом текущего контекста. Сохранение ID источника без содержательного ограничения не считается сохранением знания.

| Тип записи | Что сохраняется и что означает проверка |
|---|---|
| Факт документации | Точная выдержка или сигнатура, версия и адресуемый участок источника. Контроллер проверяет совпадение текста, хешей и версии; это подтверждает происхождение, а не универсальность вывода |
| Проектная рекомендация | Отдельно помеченная карточка с условиями, противопоказаниями и подтверждающими источниками. Автор карточки проверяет смысловую связь; контроллер проверяет ссылки и вычислимые условия. Невычислимая применимость остаётся неизвестной |
| Гипотеза агента | Предположение с наблюдением, ожидаемым эффектом и способом проверки. Сохраняется как непроверенная гипотеза и не повышается до документированного факта |
| Результат эксперимента | Исход, разрешённые метрики и артефакты, подтверждённые контроллером. Результат относится к записанным данным, протоколу, среде и конфигурации |

- Минимальная запись содержит ID, тип, содержательную выдержку или утверждение, источник и участок текста либо ID эксперимента, хеши и версии, условия применения и противопоказания, статус проверки и статус применимости.
- Для рекомендаций, гипотез и экспериментов записывать зависимости от `data_version`, `task_hash`, ролей признаков, `validation_hash`, окружения и `pipeline_hash`. Зависимости перечислять явно, чтобы изменение несвязанного поля не отменяло действующий факт API.
- Разделить проверку происхождения (`unchecked`, `source_verified`, `stale_source`) и применимость (`unknown`, `applicable`, `inapplicable`, `stale_context`). Наличие ссылки не означает применимость или успешную экспериментальную проверку.
- При смене корпуса или версии библиотеки повторно проверить источник и версию. При смене данных, ролей, схемы валидации, окружения или конфигурации пересчитать зависимые условия. Например, переход к временной валидации отменяет применимость рекомендации с обычным случайным cross-fitting даже при неизменном корпусе.
- Устаревшие записи сохранять в истории вместе с причиной, но не передавать как действующее основание для решения. Противоречия не перезаписывать молча; показывать их и требуемую проверку.
- После другого инструмента, сокращения контекста и перезапуска сохранять необходимые выдержки и ограничения с источниками. Повторная передача уже известной записи не обнуляет счётчики отсутствия прогресса.
- Раздельно записывать предоставление материала, ссылку агента на него и применение либо отклонение. Применение подтверждается наблюдаемым изменением конфигурации или кода и исполнением; ID в гипотезе сам по себе этого не доказывает.

## 6. Проверки и критерии приёмки

**Технические и содержательные проверки**

- Проверить происхождение, точные версии, конечный перечень разделов, статусы покрытия, лицензии и воспроизводимость в двух чистых каталогах. Отдельно проверить ресурсные бюджеты полного корпуса и реальной поставки.

- Проверить память на содержательном ограничении: прочитать его, выполнить другой инструмент, сократить контекст, перезапустить процесс и проверить фактический следующий запрос модели. Дополнительно менять валидацию и конфигурацию при прежнем корпусе и проверять пересчёт применимости.
- Прежний тест метаданных сохранить как вспомогательный; требование отсутствия содержания в каждой записи памяти заменить проверкой ограниченного объёма содержательных выдержек. Добавить проверки, что гипотеза не становится фактом и таймаут не считается доказательством низкого качества метода.
- Проверить, что несовместимая рекомендация обоснованно отклоняется, известное обязательное предупреждение не исчезает при сокращении и недостаточный по эталонной разметке пакет не проходит оценку достаточности. Отдельно проверить, что `answer_usable=true` не превращает неизвестную применимость в подтверждённую и не заменяет оценку полноты. Проверять фактический сериализованный запрос, отправляемый через транспорт модели.
- Выполнить существующий технический набор проверок в среде с точными зависимостями организаторов.

**Разметка и метрики поиска и выдачи**

- Прежние 40 запросов использовать как разработочный и регрессионный набор. Переименовать метрику попадания одного ожидаемого `doc_id` в `Hit@5`; исторические отчёты не переписывать.
- Добавить 60 заранее размеченных запросов и разделить их на 30 разработочных и 30 отложенных. В каждой части: 12 положительных с одним достаточным источником, 8 с сочетанием сведений, 5 посторонних или отсутствующих в корпусе и 5 случаев неправильной версии либо неоднозначного API.
- Для каждого положительного запроса заранее определить обязательные атомарные сведения, условия и предупреждения с подтверждающими участками. Разметка явно задаёт OR для взаимозаменяемых источников и AND для дополняющих друг друга сведений. Одна найденная ссылка не заменяет все необходимые сведения.
- Для каждого положительного запроса, включая прежние 40 и обе части новых запросов, подготовить эталонный пакет из точных материалов целевого корпуса. Он должен содержать все обязательные сведения, условия, предупреждения и метаданные и после канонической сериализации помещаться максимум в три материала и 6000 символов. Сохранить его состав, хеш, размер и успешный результат оценивания; наличие такого пакета обязательно до включения задания в основную приёмку.
- Проверить, что эталонный пакет проходит путь подготовки фактического контекста без потери необходимых сведений. Если пакет изначально не помещается или нужных сведений нет в целевом корпусе, исправить задание и разметку до их фиксации; не учитывать это как ошибку агента. Потеря помещавшихся сведений при обработке пакета считается ошибкой реализации. Эталоны хранить только в проверочном контуре, не передавать агенту и не использовать отложенные эталоны для настройки ранжирования. Назначение эталона — проверка корректности оценивания, как описано в [руководстве Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents).
- Раздельно измерять поиск до упаковки (`Hit@5`, а при полном множестве релевантных документов также настоящий `Recall@5`) и достаточность окончательного пакета из максимум трёх материалов и 6000 символов после всех сокращений. Достаточность означает наличие всех требуемых сведений, условий, предупреждений и правильных версий в реально переданном тексте.
- Основной порог на отложенных положительных запросах: не менее 95% достаточных окончательных пакетов. Для заранее помеченных критических ограничений и версий требовать 100%; случай с потерянным обязательным предупреждением считается провалом независимо от попадания документа в первую пятёрку.
- Для отрицательных запросов отдельно считать ошибочную уверенную выдачу и неправильное принятие версии. На отложенном наборе требовать ноль таких случаев; корректный отказ или явно обозначенные варианты неоднозначного имени не считаются ошибкой.
- Зафиксировать хеши разметки, версий корпуса и ранжирования до итоговой проверки. Отложенную часть не использовать при подборе параметров; после её раскрытия не представлять повторную проверку того же набора как новое независимое подтверждение.

**Живая приёмка: наблюдаемые исходы**

Проверять конфигурацию, код, артефакты и фактическое исполнение. Корректная ссылка или пересказ без необходимого действия не закрывают сценарий.

- Для каждого сценария подготовить известную рабочую эталонную последовательность максимум из шести решений с тем же обязательным исходом. До основной серии подтвердить её исполнение из подготовленной поставки нового варианта через реальные инструменты и оценщик, воспроизводя заранее заданные команды без дополнительной серии Qwen. Время холодного запуска, восстановления, подготовки и исполнения вместе с заранее зафиксированным резервом на ответы Qwen должно помещаться в 180 секунд; резерв обосновать доступными измерениями канала, а время воспроизведения учитывать отдельно.
- Сохранить эталонную последовательность, артефакты, фактическое число решений, время, резерв и результат проверки. Если выполнимость не подтверждена, исправить сценарий до фиксации приёмочной серии. Эталон не передавать агенту и не использовать как единственную допустимую траекторию: оценивать результат, принимая заранее разрешённые альтернативы. Успех воспроизведения команд не считать подтверждением надёжности или задержек настоящего Qwen.
